# Route / Page Inventory

## 1. Current Status

Status: `frontend_route_baseline_implemented`.

Implementation date: `2026-06-09`; latest route update: `2026-06-22`.

Scope decision: the active navigation baseline includes `我的工作 / 工作概览 / 我的任务 / 待我提交 / 待我验收 / 我的档案 / 我的薪资 / 我的绩效`, `人员组织`, `客户管理`, `任务管理 / 任务看板 / 任务列表 / 人员任务 / 任务反馈`, `绩效管理 / 绩效看板 / 绩效规则 / 绩效签署 / 绩效明细`, `薪酬社保 / 薪酬总览 / 薪酬明细 / 社保公积金`, `财务管理 / 财务总览 / 经营总览 / 财务统计 / 应收应付 / 收支流水 / 流水复核 / 资金处理 / 对公账户 / 银行对账`, `税务管理 / 发票台账 / 发票匹配 / 申报准备 / 税务办理`, plus `系统管理 / 业务角色 / 任务配置 / 工作日历 / 财务类目 / 对公账户配置 / 社保公积金配置 / 税务口径`. `我的工作` is the employee-facing self-service work area: it summarizes the current employee's active tasks, archive information, monthly salary results, and non-editable performance information; `/my-work/task-submit` owns current-employee task submission, and `/my-work/task-acceptance` owns current-employee acceptance, rejection, and source task scoring. The active `人员组织` submodules are `人员总览`, `人员档案`, `人事异动`, `岗位管理`, `考勤假勤`, and `考勤月报`. `到期管理` no longer appears as a standalone submodule: probation, labor-contract, cooperation-agreement, and performance-rule-derived termination-condition reminders are integrated into `人员总览` as personnel risk summary, expiry-risk filtering, and detail-drawer reminder data. `岗位管理` remains personnel-organization business master data and is intentionally not placed under `系统管理`, because system management only owns account, business-role package, calendar, task, finance-category, public-account, social-insurance configuration, and read-only tax-policy surfaces. The active `客户管理` submodules are `客户档案`, `品牌管理`, `门店管理`, and `合同管理`. The active `任务管理` submodules are `任务看板`, `任务列表`, `人员任务`, and `任务反馈`; `任务看板` is a read-only task-pool health and operations-risk dashboard, while `任务反馈` is an已完成任务 feedback archive that merges internal acceptance rework and client-side feedback counts by task. `任务提交`, `任务验收`, standalone `任务计分`, and standalone `甲方反馈` are not active task-management navigation modules. Task performance scoring is intentionally handled inside `/my-work/task-acceptance` when acceptance passes, not as a standalone navigation module. The active `薪酬社保` submodules are `薪酬总览`, `薪酬明细`, and `社保公积金`: `薪酬总览` consumes salary detail rows as a read-only executive overview of salary sections and employee salary ranking; `薪酬明细` consumes personnel salary profiles, attendance monthly reports, in-month manual salary adjustments, confirmed social-insurance/housing-fund personal-share records, and confirmed employee personal-income-tax withholding records to produce employee-month salary result rows; `社保公积金` owns employee-level monthly confirmation, official payment entry, payment voucher upload, and payment cash-flow linkage in one module, with employee confirmation shown in the detail drawer tab instead of a separate navigation item. One-off salary adjustment is maintained inside `薪酬明细` through the table primary action; `/salary/adjustments` is a legacy redirect and is not shown in navigation. The active `财务管理` submodules are `财务总览`, `经营总览`, `财务统计`, `应收应付`, `收支流水`, `流水复核`, `资金处理`, `对公账户`, and `银行对账`; the active `税务管理` submodules are `发票台账`, `发票匹配`, `申报准备`, and `税务办理`. Finance category definitions are maintained under `系统管理 / 财务类目`, official company public-bank-account definitions are maintained under `系统管理 / 对公账户配置`, Wuhan social-insurance/housing-fund policy parameters are maintained under `系统管理 / 社保公积金配置`, and the current read-only tax-policy display is maintained under `系统管理 / 税务口径`; these system pages are consumed by finance, salary-social-insurance, and tax pages. Working-day calendars are maintained under `系统管理 / 工作日历` as full-time task-availability configuration. `考勤假勤` records full-time personnel attendance and leave availability facts; `考勤月报` consumes working-day defaults plus those exception facts and separate payroll-attendance adjustments to derive monthly payable-attendance summaries, with hours as the salary-calculation unit and days as an auxiliary display. `考勤月报` list is a result ledger with no row operation column; payroll-attendance adjustment is opened through the table primary action, then scoped by month and personnel. Settlement lock is supplied by `薪酬社保 / 薪酬明细` settlement state and is not rendered as a personnel-side list or detail field. `业务范围`, `服务配置`, `组织架构`, standalone `到期管理`, and the former standalone `任职合作` module are intentionally not routed. Other business modules are intentionally not routed yet.

Personnel frontend domain boundary: before backend integration, personnel pages consume stable business rules through `apps/web/src/features/people/peopleDomain.ts` and seed data through `peopleRepository.ts`. Page components must not directly import raw personnel mock data. `PeopleOrganizationProvider` remains the frontend-session state owner, while `peopleDomain.ts` owns derivations such as archive list status, attendance eligibility/status/effect, overview availability, work-calendar display, task-access status, movement effects, and position member counts. This is still frontend prototype logic and is not an API, database, authorization, or audit-persistence contract.

Task frontend domain boundary: before backend integration, task pages consume stable frontend task rules through `apps/web/src/features/tasks/taskDisplayModel.ts`, `taskDashboardModel.ts`, `taskAcceptanceModel.ts`, `taskFeedbackModel.ts`, `taskFileModel.ts`, and `taskOperationModel.ts`, plus task-specific shared components under `apps/web/src/features/tasks/components`. `TaskManagementProvider` remains the frontend-session state owner, while the task domain models own closed/overdue derivation, task type/store display helpers, dashboard metric/trend/risk/load aggregation, acceptance scoring/rejection blockers, completed-task feedback archive aggregation, Feishu file-link record construction, business-server screenshot record construction, and operation-record append behavior. Task pages should not reintroduce page-local copies of those rules. This is still frontend prototype logic and is not an API, database, authorization, dispatch, Feishu integration, or audit-persistence contract.

Current `/people/attendance` contract:

- Purpose: full-time attendance and leave ledger under `人员组织`, used to record time-boxed leave, compensatory rest, make-up workday, or temporary unavailability for full-time personnel.
- Boundary: this page is not a punch-clock system, attendance device integration, payroll deduction module, overtime salary calculator, monthly attendance report, or OA approval engine. It records frontend-session full-time attendance and leave availability facts only. Part-time partners are intentionally excluded from this time-boxed constraint entry; their task assignment is constrained by cooperation status, task participation, and person-level task capability. Downstream modules may consume these facts, but downstream selection, workload, and capability rules belong to those modules' own contracts. Backend persistence, approval workflow, permission enforcement, and scheduler-grade workload calculation remain pending.
- Data ownership baseline: `PeopleOrganizationProvider` owns frontend-session `attendanceRecords` alongside personnel, position, and movement state. Each record references a `PeopleMember` by id and stores record type, availability effect, start/end time, derived duration, derived status, record mode, recorder, recorded time, reason, optional editor/edit time, and optional cancel actor/reason/time.
- Metrics: `当前不可用`, `待生效`, `本月记录`, `临时不可用`, and `已结束`.
- Filters: compact inline filters for `生效时间`, `类型`, `状态`, and keyword. `生效时间` uses the shared date-scope control with `全部`, `当月`, `按月份`, and `按时间段`; `全部` means no date restriction, `当月` uses the page's current frontend baseline month, `按月份` filters records whose start/end range intersects the selected month, and `按时间段` filters records whose start/end range intersects the selected date range. The list does not render a personnel selector; personnel can still be searched by keyword through name, work number, and position. Keyword search also includes type and reason; phone number is not part of the attendance list/search surface. Filter changes apply immediately and no separate query/reset workflow is rendered.
- Table columns: `员工工号`, `人员`, `类型`, `时间范围`, `时长`, `状态`, `原因`, and `记录信息`. `员工工号` is an independent column. The personnel cell shows name and position only; phone numbers, internal record ids, and list-level latest-update time are not shown. Row click opens a read-only detail drawer.
- Interaction baseline: toolbar exposes one primary `新增记录` entry. Create mode chooses `记录方式` inside the drawer: `日常记录` uses active full-time personnel and derives `待生效 / 生效中 / 已结束` from start/end time; `历史补录` can select all full-time personnel, derives `已结束`, and cannot end later than the current frontend baseline time. Users do not manually select status. The form shows derived `记录状态` only after start/end time is complete and the duration is valid. Record type options are `请假`, `调休`, `补班`, and `临时不可用`; `补班` still derives backend-facing availability effect `可用`; other record types derive `不可用`, but the page does not render a separate `影响` column or summary card. Edit mode locks the linked personnel as read-only; correcting the wrong person requires canceling the old record and adding a new one. Edit-mode `取消` returns to read-only detail. `取消记录` is a distinct detail action that requires a cancel reason and marks a record `已取消`.
- Detail baseline: the drawer uses shared summary cards, detail info grid, and operation-record table. Summary cards show `人员`, `类型`, and `时长`. The detail grid is split into `人员范围` and `假勤记录`: `人员范围` shows `员工工号`, `岗位`, and `适用日历`; `假勤记录` shows start/end time, record mode, reason, and cancel reason when applicable. Personnel archive attributes such as `员工类别`, and operation metadata such as record date, recorder, latest editor, cancel actor, and cancel time are not duplicated in the info grid; generated operation history is the source for those actor/time facts. Operation history keeps the original recorded time, edit time, and cancel time separate. The module does not render review, approval, audit, or pending-processing states.

- Detail shape: clicking a row opens a read-only drawer with compact summary cards and tabs `账户流水`, `业务来源`, `凭证文件`, and `操作记录`. The page does not expose `新增`, `复核`, `作废`, `登记转入`, `登记报销`, or real bank actions.
- Data boundary: this page reuses frontend session finance rows. It does not fetch bank balances, import bank statements, perform reconciliation, execute transfers, persist backend records, or produce audit-grade account evidence.

Current `/finance/bank-reconciliation` contract:

- Page label: `银行对账`.
- Purpose: bank-statement reconciliation workbench that compares imported real-bank-statement rows with system-side public-account transaction rows. The row object in the main workbench is a bank statement row, not a business income/expense transaction.
- Import baseline: uploaded Excel/CSV files enter a bank-statement pool through an import preview. Importing bank statements does not create `收支流水`, does not change system transaction amounts, and does not count as business income or expense. Imported rows are evidence candidates for reconciliation only.
- Account source baseline: imported batch and statement examples use the default configured public-account display name from `/system/public-accounts`; real bank-account matching from uploaded file metadata is deferred.
- Matching baseline: matching uses amount, direction, date, counterparty name, and bank summary as visible criteria. Match statuses include `待确认`, `已对账`, `银行未匹配`, `系统未匹配`, `金额异常`, `重复导入`, and `暂不可对账`. Rows whose matched system transaction is still `待复核` are shown as `暂不可对账` under `待处理` and cannot bypass `/finance/review`.
- Process baseline: the lightweight matching flow is `导入预览` -> `进入银行流水池` -> `处理待处理项`. The workbench exposes `处理建议` for each bank row, such as `人工确认`, `等待流水复核`, `补登记系统流水`, `核对银行流水`, `确认重复`, or `核对异常`. Most suggestions are guidance states in this prototype. `确认对账` and `撤销对账` are the current real frontend-session operations and must write operation records.
- Candidate baseline: bank-statement detail shows a compact `候选系统流水` table generated from visible criteria. Candidate rows are suggestions for manual review, not automated accounting or audit evidence.
- Confirm baseline: `人工确认` can become a real frontend operation only when the system transaction is `已入账`, the bank/system directions match, the amount difference is `0`, and neither side has already been confirmed elsewhere. Confirming changes the bank row to `已对账`, updates the matched system transaction to `已对账`, and appends an operation record containing actor, time, bank serial number, system transaction number, and status transition.
- Reversal baseline: `撤销对账` is available only for `已对账` rows. It requires a reason, changes the bank row back to `待确认`, changes the matched system transaction back to `未对账`, and appends an operation record with the reversal reason. This is a lightweight correction entry, not a closed-period accounting reversal workflow.
- Metrics: `银行流水`, `导入净额`, `已对账`, `待处理`, and `异常`. The `导入净额` is bank-side imported net movement for the visible period and is not the business operating net.
- Filters: `流水期间`, `匹配状态`, and keyword.
- Tabs: `待处理`, `已对账`, `对账异常`, `银行流水`, and `导入记录`. `待处理` covers `待确认`, `暂不可对账`, `银行未匹配`, and `系统未匹配`; `银行流水` is the imported bank-statement pool; `导入记录` tracks import batches and row counts.
- Detail shape: clicking a bank-statement row opens a workflow-processing drawer with `匹配结果`, `银行流水`, `系统流水`, and `对账记录`. `匹配结果` contains match status, match degree, difference, `处理建议`, and `候选系统流水`. If no system transaction is matched, the drawer explicitly shows no matched system public-account flow and points users toward补登记或核对导入范围. The drawer uses the shared workflow action contract for `关闭`, `确认对账`, and `撤销对账`; the page does not assemble Drawer footer or detail-layout classes directly.
- Data boundary: this page uses frontend mock bank statements and active-session system transactions only. It does not parse real Excel content, call bank APIs, perform automated reconciliation persistence, generate accounting vouchers, mutate backend data, or provide audit-grade bank reconciliation evidence.

## 6. Cross-Page Rules

- Route/page changes must update this file in the same change.
- Navigation must remain at least two levels: main module and submodule.
- New business modules must not be added to navigation until the user confirms the module boundary.
- Static mock data must be replaced with typed API contracts before backend integration.
- Auth hiding in UI is not sufficient; future protected routes must pair frontend route guards with backend authorization.
- Personnel organization cross-page state is currently active-session frontend state only. `PeopleOrganizationProvider` owns personnel rows, position rows, and movement effects for prototype linkage; it is not persistence, backend authorization, audit storage, or data-contract evidence.
