# Route / Page Inventory

## 1. Current Status

Status: `frontend_route_baseline_implemented`.

Implementation date: `2026-06-09`; latest route update: `2026-07-10`.

Scope decision: the active navigation baseline includes `我的工作 / 工作概览 / 我的任务 / 待我提交 / 待我验收 / 费用与代收 / 费用报销审核 / 我的档案 / 我的薪资 / 我的绩效`, `人员组织`, `客户管理`, `任务管理 / 任务看板 / 任务列表 / 人员任务 / 任务反馈`, `绩效管理 / 绩效看板 / 绩效规则 / 签署档案 / 绩效明细`, `薪酬社保 / 薪酬总览 / 薪酬明细 / 社保公积金`, `财务管理 / 经营总览 / 应收应付 / 收支流水 / 流水复核 / 银行对账 / 账户台账 / 会计科目 / 会计凭证 / 总账 / 期间结账 / 财务报表`, `税务管理 / 发票台账 / 申报准备 / 税务办理`, plus `系统管理 / 业务角色 / 任务配置 / 工作日历 / 账套初始化 / 财务类目 / 对公账户配置 / 社保公积金配置 / 税务口径`. `我的工作` is the employee-facing self-service work area: it summarizes the current employee's active tasks, archive information and monthly salary results, exposes current formal performance results for employee confirmation or objection, and owns employee-originated finance matters; `/my-work/task-submit` owns current-employee task submission, `/my-work/task-acceptance` owns current-employee acceptance, rejection, and source task scoring, `/my-work/expense-collection` owns current-employee费用报销、代收登记草稿与提交, and `/my-work/expense-review` owns current reviewer reimbursement audit only. The active `人员组织` submodules are `人员总览`, `人员档案`, `人事异动`, `岗位管理`, `考勤假勤`, and `考勤月报`. `到期管理` no longer appears as a standalone submodule: probation, labor-contract, cooperation-agreement, and performance-rule-derived termination-condition reminders are integrated into `人员总览` as personnel risk summary, expiry-risk filtering, and detail-drawer reminder data. `岗位管理` remains personnel-organization business master data and is intentionally not placed under `系统管理`, because system management only owns account, business-role package, calendar, task, finance-category, public-account, social-insurance configuration, and read-only tax-policy surfaces. The active `客户管理` submodules are `客户档案`, `品牌管理`, `门店管理`, and `合同管理`. The active `任务管理` submodules are `任务看板`, `任务列表`, `人员任务`, and `任务反馈`; `任务看板` is a read-only task-pool health and operations-risk dashboard, while `任务反馈` is an已完成任务 feedback archive that merges internal acceptance rework and client-side feedback counts by task. `任务提交`, `任务验收`, standalone `任务计分`, and standalone `甲方反馈` are not active task-management navigation modules. Task performance scoring is intentionally handled inside `/my-work/task-acceptance` when acceptance passes, not as a standalone navigation module. The active `薪酬社保` submodules are `薪酬总览`, `薪酬明细`, and `社保公积金`: `薪酬总览` consumes salary detail rows as a read-only executive overview of salary sections and employee salary ranking; `薪酬明细` consumes personnel salary profiles, attendance monthly reports, in-month manual salary adjustments, confirmed social-insurance/housing-fund personal-share records, and confirmed employee personal-income-tax withholding records to produce employee-month salary result rows; `社保公积金` owns employee-level monthly confirmation, official payment entry, payment voucher upload, and payment cash-flow linkage in one module, with employee confirmation shown in the detail drawer tab instead of a separate navigation item. One-off salary adjustment is maintained inside `薪酬明细` through the table primary action; `/salary/adjustments` is a legacy redirect and is not shown in navigation. The active `财务管理` submodules are `经营总览`, `应收应付`, `收支流水`, `流水复核`, `银行对账`, `账户台账`, `会计科目`, `会计凭证`, `总账`, `期间结账`, and `财务报表`; `/finance` and legacy `/finance/overview` enter `经营总览`, `/finance/account-ledger` owns account-first company public-account ledger, `/finance/accounting-subjects` owns accounting-subject master data, `/finance/accounting-vouchers` owns frontend accounting-voucher statusized generation from business confirmations, matched invoice facts, reviewed and bank-reconciled cash-flow rows, confirmed tax-handling facts, and frontend-session记账、冲销、闭期后续调整 lifecycle overlay; closed-period pre-lifecycle rows are readback-only and the lock is frontend-session state until backend period APIs exist. `/finance/general-ledger` owns read-only period-based subject balances and subject detail entries derived only from `已记账` accounting vouchers, `/finance/period-close` owns restrained period-close checks and frontend-session period locking after voucher booking, general-ledger trial balance, cash reconciliation, tax-handling checks, and social-insurance/housing-fund checks pass, `/finance/financial-statements` owns read-only trial/close-readback financial statements derived only from booked general-ledger subject balances, and `/finance/public-account`, `/finance/statistics`, `/finance/reports`, `/finance/handled-funds`, and `/finance/fund-handling` are intentionally removed without redirects. The active `税务管理` submodules are `发票台账`, `申报准备`, and `税务办理`; invoice-to-business association is handled inside `发票台账` and `应收应付` detail drawers. Account-set initialization is maintained under `系统管理 / 账套初始化`; finance category definitions are maintained under `系统管理 / 财务类目`, official company public-bank-account definitions are maintained under `系统管理 / 对公账户配置`, Wuhan social-insurance/housing-fund policy parameters are maintained under `系统管理 / 社保公积金配置`, and the current read-only tax-policy display is maintained under `系统管理 / 税务口径`; these system pages are consumed by finance, salary-social-insurance, and tax pages. Working-day calendars are maintained under `系统管理 / 工作日历` as full-time task-availability configuration. `考勤假勤` records full-time personnel attendance and leave availability facts; `考勤月报` consumes working-day defaults plus those exception facts and separate payroll-attendance adjustments to derive monthly payable-attendance summaries, with hours as the salary-calculation unit and days as an auxiliary display. `考勤月报` list is a result ledger with no row operation column; payroll-attendance adjustment is opened through the table primary action, then scoped by month and personnel. Settlement lock is supplied by `薪酬社保 / 薪酬明细` settlement state and is not rendered as a personnel-side list or detail field. `业务范围`, `服务配置`, `组织架构`, standalone `到期管理`, standalone `财务统计`, standalone `资金处理`, standalone `经办资金`, and the former standalone `任职合作` module are intentionally not routed through active navigation. Other business modules are intentionally not routed yet.

`发票匹配` and `/tax/invoice-matching` were hard-removed on 2026-07-10 without redirect. Invoice-to-business association is an action shared by `发票台账` and `应收应付` detail drawers, documented in `docs/governance/invoice-association-hardcut-v1.md`.

Personnel frontend domain boundary: before backend integration, personnel pages consume stable business rules through `apps/web/src/features/people/peopleDomain.ts` and seed data through `peopleRepository.ts`. Page components must not directly import raw personnel mock data. `PeopleOrganizationProvider` remains the frontend-session state owner, while `peopleDomain.ts` owns derivations such as archive list status, attendance eligibility/status/effect, overview availability, work-calendar display, task-access status, movement effects, and position member counts. This is still frontend prototype logic and is not an API, database, authorization, or audit-persistence contract.

Task frontend domain boundary: before backend integration, task pages consume stable frontend task rules through `apps/web/src/features/tasks/taskDisplayModel.ts`, `taskDashboardModel.ts`, `taskAcceptanceModel.ts`, `taskFeedbackModel.ts`, `taskFileModel.ts`, and `taskOperationModel.ts`, plus task-specific shared components under `apps/web/src/features/tasks/components`. `TaskManagementProvider` remains the frontend-session state owner, while the task domain models own closed/overdue derivation, task type/store display helpers, dashboard metric/trend/risk/load aggregation, acceptance scoring/rejection blockers, completed-task feedback archive aggregation, Feishu file-link record construction, business-server screenshot record construction, and operation-record append behavior. Task pages should not reintroduce page-local copies of those rules. This is still frontend prototype logic and is not an API, database, authorization, dispatch, Feishu integration, or audit-persistence contract.

## 5. Page Contract Baseline

All implemented pages are static frontend baseline pages using mock data. Personnel archive examples are plaintext fake values for prototype review and must not be treated as real personal data or production privacy evidence. The pages exist to validate shell, navigation, topbar actions, breadcrumb, dense workbench layout, compact filtering, type-dependent personnel status tags, table density, detail drawer/panel composition, and Ant Design Pro visual direction.

Current `/people/attendance` contract:

- Purpose: full-time attendance and leave ledger under `人员组织`, used to record time-boxed leave, compensatory rest, make-up workday, or temporary unavailability for full-time personnel.
- Boundary: this page is not a punch-clock system, attendance device integration, payroll deduction module, overtime salary calculator, monthly attendance report, or OA approval engine. It records frontend-session full-time attendance and leave availability facts only. Part-time partners are intentionally excluded from this time-boxed constraint entry; their task assignment is constrained by cooperation status, task participation, and person-level task capability. Downstream modules may consume these facts, but downstream selection, workload, and capability rules belong to those modules' own contracts. Backend persistence, approval workflow, permission enforcement, and scheduler-grade workload calculation remain pending.
- Data ownership baseline: `PeopleOrganizationProvider` owns frontend-session `attendanceRecords` alongside personnel, position, and movement state. Each record references a `PeopleMember` by id and stores record type, availability effect, start/end time, derived duration, derived status, record mode, recorder, recorded time, reason, optional editor/edit time, and optional cancel actor/reason/time.
- Metrics: `当前不可用`, `待生效`, `本月记录`, `临时不可用`, and `已结束`.
- Filters: compact inline filters for `生效时间`, `类型`, `状态`, and keyword. `生效时间` uses the shared date-scope control with `全部`, `当月`, `按月份`, and `按时间段`; `全部` means no date restriction, `当月` uses the page's current frontend baseline month, `按月份` filters records whose start/end range intersects the selected month, and `按时间段` filters records whose start/end range intersects the selected date range. The list does not render a personnel selector; personnel can still be searched by keyword through name, work number, and position. Keyword search also includes type and reason; phone number is not part of the attendance list/search surface. Filter changes apply immediately and no separate query/reset workflow is rendered.
- Table columns: `员工工号`, `人员`, `类型`, `时间范围`, `时长`, `状态`, `原因`, and `记录信息`. `员工工号` is an independent column. The personnel cell shows name and position only; phone numbers, internal record ids, and list-level latest-update time are not shown. Row click opens a read-only detail drawer.
- Interaction baseline: toolbar exposes one primary `新增记录` entry. Create mode chooses `记录方式` inside the drawer: `日常记录` uses active full-time personnel and derives `待生效 / 生效中 / 已结束` from start/end time; `历史补录` can select all full-time personnel, derives `已结束`, and cannot end later than the current frontend baseline time. Users do not manually select status. The form shows derived `记录状态` only after start/end time is complete and the duration is valid. Record type options are `请假`, `调休`, `补班`, and `临时不可用`; `补班` still derives backend-facing availability effect `可用`; other record types derive `不可用`, but the page does not render a separate `影响` column or summary card. Edit mode locks the linked personnel as read-only; correcting the wrong person requires canceling the old record and adding a new one. Edit-mode `取消` returns to read-only detail. `取消记录` is a distinct detail action that requires a cancel reason and marks a record `已取消`.
- Detail baseline: the drawer uses shared summary cards, detail info grid, and operation-record table. Summary cards show `人员`, `类型`, and `时长`. The detail grid is split into `人员范围` and `假勤记录`: `人员范围` shows `员工工号`, `岗位`, and `适用日历`; `假勤记录` shows start/end time, record mode, reason, and cancel reason when applicable. Personnel archive attributes such as `员工类别`, and operation metadata such as record date, recorder, latest editor, cancel actor, and cancel time are not duplicated in the info grid; generated operation history is the source for those actor/time facts. Operation history keeps the original recorded time, edit time, and cancel time separate. The module does not render review, approval, audit, or pending-processing states.

Current `/people/attendance-monthly` contract:

- Purpose: monthly payroll-attendance result ledger under `人员组织`, used to derive full-time monthly payable-attendance summaries from work-calendar defaults, `考勤假勤` exceptions, and separate monthly payroll-attendance adjustments. Payroll hours are retained as the calculation unit for downstream salary; day counts are display equivalents.
- Boundary: this page is not a punch-clock import page, OA approval workflow, salary settlement execution page, social-insurance deduction page, or task workload detail page. Salary settlement lock is consumed only as an adjustment/confirmation eligibility rule and is not rendered as a list/detail field.
- Filters: compact inline filters for `月份`, `状态`, and keyword. `月份` uses the shared month-picker control from `DateFilterFields`; the month is required because the page builds one monthly result set at a time. Keyword matches name, work number, position, and status.
- Metrics: `月报人员`, `应出勤`, `计薪出勤`, `未覆盖调休`, `调整记录`, `已确认`, and `待确认`.
- Table columns: `员工工号`, `人员`, `月份`, `应出勤`, `请假`, `调休`, `未覆盖调休`, `补班`, `临时不可用`, `人工调整`, `计薪出勤`, and `状态`. `员工工号` is an independent column. The personnel cell shows name and position only. `请假`, `调休`, `未覆盖调休`, `补班`, `临时不可用`, and `计薪出勤` display payroll hours plus equivalent days. The list remains a result ledger with no row operation column.
- Interaction baseline: toolbar exposes one primary `新增调整` entry. The adjustment drawer uses the same shared month-picker control for `月份`, then selects personnel within that month. If the corresponding salary row is settled, the report is locked and the adjustment save is disabled.
- Detail baseline: row click opens a read-only drawer with tabs `概览`, `例外明细`, `调整记录`, and `计算说明`. The detail overview keeps result identification fields such as `月份`, `人员`, `员工工号`, `岗位`, and `适用工作日历`, and shows payroll-hour facts for leave, make-up work, compensatory-rest coverage, uncovered compensatory rest, and payable attendance, but stays result-oriented and does not render employee-category, default-attendance, salary-settlement, task, or payroll-execution fields. Make-up work creates compensatory-rest credit in chronological order, compensatory rest consumes existing credit, and uncovered compensatory-rest hours enter payroll-attendance deduction. Negative compensatory-rest balance is not supported in the current frontend baseline.

Current `/customers/archives` contract:

- Purpose: customer master-data index for customer account, contract-derived cooperation state, related brands/stores, industry context, and multi-contact ownership.
- Data association baseline: customer management pages share one frontend session state through `CustomerManagementProvider`. `客户档案`, `品牌管理`, `门店管理`, and `合同管理` read/write the same customer, brand, store, and contract rows in the current browser session. Static mock data is only the seed source, not an active page-level data silo.

- Filters: compact inline filters for derived `合作状态` and keyword. Filter changes apply immediately and no separate query/reset workflow is rendered in this first customer baseline.
- Table columns: `客户`, derived `合作状态`, `联系人`, `所属行业`, `品牌`, `门店`, `对接人`, and `最近更新`. The customer code remains a neutral customer identifier and is not an internal database id. The list shows the primary contact and keeps the cell within two lines; additional contacts are indicated by count.

Create mode does not render a `合作状态` field. Row click opens a read-only customer preview drawer with vertical `客户资料`, `联系人`, and `关联品牌` sections rather than tabs; the preview footer exposes `编辑客户`, which switches to the same maintenance drawer with existing values. The customer profile section uses a softened description grid rather than a heavy form-table look; the contact table stays compact and centered; the related-brand table keeps brand name/code as the left-aligned primary column while status and store count stay centered. Tables retain light header background, subtle border, and internal horizontal scroll when needed.
- Boundary: this page does not manage customer contracts, customer finance, receivables, task acceptance, rule execution, or customer-specific permission enforcement. Cooperation status is only a frontend-derived read model from `/customers/contracts`; contract summary, settlement cycle, and contract-file handling stay out of `客户档案`.

Edit-mode `取消` or drawer close exits maintenance mode and returns to the read-only preview drawer, while create-mode cancel closes the maintenance drawer. Brand status and internal owner are not user-managed fields in this module. Create/edit updates only active-session frontend state and returns to preview after save.

Current `/customers/contracts` contract:

Current `/finance/bank-reconciliation` contract:

- Page label: `银行对账`.
- Purpose: bank-statement import and reconciliation to-do workbench that compares imported real-bank-statement rows with system-side public-account transaction rows. The active row object is a bank statement row, not a business income/expense transaction.
- Import baseline: uploaded Excel/CSV files enter a bank-statement pool through an import drawer with one selected company public account, bank-statement date range, file requirements, import precheck, and import preview. The import action is intentionally free-form: operators may import one month, several months, or a small historical supplement file for the selected account. The first frontend version rejects mixed-account files by blocking rows whose imported account name does not match the selected public account. The page only provides guidance from system-side reviewed-but-unreconciled public-account flows for the selected account, such as suggested periods to supplement, and the import drawer compares preview-covered statement periods with those suggestions. The import batch identity is derived from the statement dates in the uploaded rows, not from the current system month or the pending system rows. The frontend import contract is owned by `financeBankImportContract.ts`: required fields are `账户名称 / 交易日期 / 银行流水号 / 收支方向 / 交易金额 / 对方户名 / 摘要`, and the import unique key is `publicAccountId + bankSerialNo`, not bank serial number alone and not mutable account display name alone. Precheck verifies selected-account match, required bank-statement fields, duplicate unique keys from existing rows or the same file, date coverage, and importable row count. Account or required-field failures block import; duplicate unique keys are skipped instead of being inserted again; amount or matching exceptions can still enter the reconciliation to-do pool as handling items. Importing bank statements does not create `收支流水`, does not change system transaction amounts, and does not count as business income or expense. Imported rows become reconciliation to-do candidates only.
- Account source baseline: imported bank-statement rows store the selected account's `publicAccountId` and `publicAccountSnapshot`. Matching candidates are scoped to the same `publicAccountId`, so two accounts can reuse the same bank serial number without colliding.
- Matching baseline: matching uses amount, direction, bank transaction date versus system occurred/accounting period, counterparty name, and bank summary as visible criteria. The UI displays only restrained operation-level states `待处理`, `待确认`, `异常`, and `已对账`; internal causes such as bank-unmatched, system-unmatched, amount exception, duplicate import, or temporarily blocked are kept as handling reasons and action suggestions instead of becoming separate visible status families. Same-day matches score highest, near-date and same-month differences can still be candidates, and cross-month candidates remain visible when amount/direction/counterparty facts are strong. A reviewed May system cash-flow row that has not yet been bank-reconciled must stay in the reconciliation queue even if the operator is working in a later month.
- Relationship baseline: each bank-statement row owns `matchedTransactionIds: string[]` instead of a single matched transaction field. Empty array means no matched system cash-flow row, the first ID is the primary matched system row shown in the detail panel, and additional IDs represent adjustment rows that participate in the same bank-statement reconciliation. This supports amount-mismatch cases where one bank statement is reconciled against the original system cash-flow row plus one or more `流水补差` rows after review.
- Process baseline: the lightweight matching flow is `导入预览` -> `进入银行流水池` -> `对账待办处理`. The main page intentionally has no date, status, keyword, or table-tab filtering, because reconciliation is a pending-work queue and must not hide historical unreconciled bank or system cash-flow rows. Unresolved bank rows are handled from a left queue and a right detail panel. The detail panel exposes `处理建议`, such as `人工确认`, `等待流水复核`, `补登记系统流水`, `核对银行流水`, `确认重复`, or `核对异常`. Quick handling is intentionally narrow: `补登记系统流水` creates a pending-review system cash-flow row from the selected bank statement without directly入账 or对账; `补充银行流水` opens the bank-import drawer for system-side rows without imported bank evidence; `查看复核进度` only shows linked pending-review cash-flow status. Amount mismatch is handled in-place by creating a `流水补差` row that enters `/finance/review`; while the adjustment row is `待复核`, the bank row remains blocked as `暂不可对账`, and after the adjustment row is `已入账` and the signed difference reaches `0`, the bank row becomes confirmable. Duplicate conflicts remain handling states and are not auto-resolved here. `确认对账` is the final frontend-session reconciliation operation and must write operation records.
- Candidate baseline: the right detail panel shows a compact `候选系统流水` table generated from visible criteria. Candidate rows are suggestions for manual review, not automated accounting or audit evidence.
- Confirm baseline: `人工确认` can become a real frontend operation only when the matched system transaction is `已入账`, the bank/system directions match, the effective amount difference is `0`, and neither side has already been confirmed elsewhere. For ordinary one-to-one matching, confirming changes the bank row to `已对账`, updates the matched system transaction to `已对账`, and appends an operation record containing actor, time, bank serial number, system transaction number, and status transition. For amount-mismatch matching, confirming writes `已对账` to the original system row plus reviewed adjustment rows listed in `matchedTransactionIds`. If the matched system transaction period is closed in the frontend session, the detail panel shows a readback-only notice and disables confirm/amount-mismatch handling; if a bank-unmatched row would need补登记系统流水 into a closed statement month, the quick action is disabled and the row stays historical review-only.
- Reversal baseline: no list-level or detail-level reversal operation is currently exposed in the active page. Historical corrections should be revisited with backend closed-period and audit requirements before restoring UI.
- Metrics: `待处理`, `待确认`, `异常`, and `已对账`. The page does not render imported net movement or business operating net.
- Filters: none on the main page. Account and bill period are captured only in the import drawer.
- Detail shape: selecting a bank-statement row updates the right panel. The panel contains bank date/amount, system period, date relationship, `对账判断`, compact `候选系统流水`, matched `系统流水`, system voucher preview/download, and operation records. `候选系统流水` shows system period and date relationship instead of exposing internal confidence as the primary decision field. - Data boundary: this page uses frontend mock bank statements and active-session system transactions only.
