# 益禾堂内部设计项目管理系统 — 第一阶段实施规格（2027）

状态：需求已确认，实施待开始。仅针对益禾堂业务；不得破坏原仓库其他客户、品牌、人员、财务业务。

## 1. 已确认的业务边界

- 甲方通过微信等渠道通知项目负责人有新门店。
- 项目负责人创建项目，填写 **所属区域、6.5整店、店铺名称、合同号、外协类型、外协设计师**，再派单。此阶段不要求设计师创建项目或重复填写基础资料。
- 设计师登录系统仅看到自己负责门店，更新项目状态、派单后各时间、审核截图、关键事项及说明。
- 项目负责人统一检查全部门店、审核设计师提交的数据，统计月份工作量。
- 高管拥有月度结算复核权限，财务信息不暴露给普通设计师。
- 甲方**不登录系统、不查看共享飞书表格、也不需要实时飞书同步**；仅在有需要时由负责人导出甲方专用数据交付。
- 所有业务数据只有一个维护入口。不得要求设计师同时维护飞书和本系统。

## 2. 与仓库现状的衔接

仓库已存在 `客户管理/门店管理`、`任务管理/任务列表`、`我的工作`、`任务提交/验收`、角色与权限入口，以及较大范围的通用财务功能。

应优先扩展现有客户/品牌/门店/任务/人员抽象，而非新建平行的“益禾堂门店任务库”。益禾堂仅为客户/品牌配置及其任务视图。现有前端部分功能为会话状态/模拟数据，不得视为已经实现持久化或服务端权限。

- Web：Vite + React + TypeScript + Ant Design（原样沿用，不迁移到 Next.js）。
- 原仓库文档：`docs/requirements/0002-business-modules-draft.md`、`docs/web/route-page-inventory.md`。
- 对接已有任务/审核组件时，区分 **出图阶段状态** 与 **审核状态**，不可用一个状态覆盖另一个。

## 3. 原始飞书 .base 文件实测结构

来源：用户提供《【昭舍】2026年门店出图台账统筹表.base》；文件格式为 JSON，顶层含 `gzipSnapshot`（Base64 + Gzip），解压后首项为 `schema`，其 `data.recordMap` 保存记录，`data.table.fieldMap` 保存字段。

实测：
- 1 个数据表：`2026年台账`；501 条记录；25 个字段；2 个视图：`门店出图台账`、`看板`。
- 原始记录中 `特殊情况说明` 有 154 条非空，不可删除或当成无数据。
- `派单时间`、`方案上传时间` 为 DateTime，值为毫秒时间戳。
- `营运确认方案时间`、`施工图上传时间` 为 Text，既有斜杠也有短横线格式，且存在字符串 `"0"`：应归一化为日期/空值，保留原始值和迁移异常记录。
- `特殊情况说明` 是多选，不是普通文本；选项 ID 应按 fieldMap.property.options 解析成中文标签，保留多选。
- 公式字段应由系统计算，不让设计师手工填。

25个原始字段（保持名称映射）：
1. 施工图出图时效（公式）
2. 特殊情况说明（多选）
3. 施工图评分
4. 营运确认方案时间
5. 城市等级
6. 是否为核心商圈
7. 门店模型
8. 施工图上传时间
9. 方案出图时效（天）（公式）
10. 外协类型
11. 方案评分
12. 备注
13. 合同号
14. 总部施工图设计师签收
15. 店铺名称
16. 所属区域
17. 父记录
18. 外协设计师
19. 设计出图项目状态
20. 全店出图时效（天）（公式）
21. 日期 3
22. 6.5整店
23. 服务类型
24. 方案上传时间
25. 派单时间

时效（单位：自然日，可保留两位小数；业务确认后再引入节假日扣减规则）：
- 方案出图时效 = 方案上传时间 - 派单时间
- 施工图出图时效 = 施工图上传时间 - 营运确认方案时间
- 全店出图时效 = 两阶段时效之和
- 日期缺失时显示“—”，不得用 0 代替实际缺失的时长。

注意：`6.5整店` 和 `外协类型` 是两种不同的分类，保持独立。

## 4. 建议的门店台账体验

- 页面1「全部门店」：负责人可新建、指派/改派、筛选/搜索/按人员和月份查看；高密度表格是默认视图。
- 页面2「我的门店」：设计师仅看本人分配的项目；列表内快速编辑出图时间和状态；点开门店详情上传材料。
- 页面3「门店详情」：基本资料（负责人可编辑） / 出图进度 / 内部审核 / 甲方审核 / 关键事项 / 操作历史。
- 页面4「数据中心」：历史 `.base` 导入预览与确认、Excel/CSV导出、按字段白名单导出甲方台账。
- 后续阶段：月度总结、费用规则、金额复核、结算锁定。

关键规则：原有单条记录应保存 `source_record_id` 用于幂等迁移；合同号/门店名称均不可单独视作唯一键，因为同一店可能存在不同任务或多次委托。

## 5. 第一阶段完成标准

1. 负责人创建益禾堂门店任务并分配真实设计师账号。
2. 设计师只能读取/更新本人负责的项目，且不能更改负责人输入的合同号、门店归属、分配信息；**服务端**校验，不只是隐藏按钮。
3. 编辑后刷新页面、重新登录，数据仍然存在（不能只有前端会话状态）。
4. 导入 .base 先预览501条的字段、数据、缺失值与重复候选，再由负责人确认执行。幂等再次导入不会重复产生项目。
5. 甲方导出采取显式白名单（门店名、合同号、区域、设计师、派单时间、各出图日期、出图时效、状态），默认不导出内部审核截图、财务与异常责任记录。
6. 导出 CSV/Excel 时处理公式注入风险；上传的附件使用服务端校验且不得通过公开 URL 绕过权限访问。
7. 最小测试范围：一名负责人+两名设计师的权限隔离；创建/派单/更新/刷新；导入预览与重复导入；日期解析与原公式；安全导出。
8. 完成后出示可运行入口、启动指令、测试结果以及未实现的后续模块。不得把设计稿/模拟数据标为生产可用。

## 6. 分阶段执行顺序（供 Codex）

- M1：核对当前任务/门店/角色和 API 模型，建立字段映射与真实的存储/权限边界。
- M2：实现负责人派单和设计师的专属台账页面（最小可用闭环）。
- M3：实现 .base 导入预览/确认与甲方导出（不要提交真实记录入库到 Git）。
- M4：在已有任务审核中增加“内部审核/甲方审核”区分与真实附件保存。
- M5：月度工作量及结算确认，单独评审财务字段和权限后实现。
