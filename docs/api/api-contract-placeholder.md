# API Contract Placeholder

## 1. Status

Status: `partial_contract_draft`.

Most backend/API contracts remain undefined. Finance bank reconciliation has a
backend-facing contract draft, funds-voucher phase 1 has a backend-facing
cash-fact contract draft, tax-basis/accounting-mapping now has a
backend-facing contract draft, accounting-voucher/general-ledger now has an
expanded backend-facing contract before implementation, and period-close phases
1-3 now have a dedicated API contract draft for backend `close-checks`,
persistent period close, and closed-period source mutation guards.

## 3. Contract Rules

- API fields must be documented before implementation.
- Validation and error semantics must be specified.
- Web consumers must be checked when contracts change.
- Contract tests are required before API readiness can be claimed.

## 3.1 Period Close Phase 1-3 Contract Boundary

`docs/api/finance-period-close-api-contract.md` is the current API draft for
period-close phases 1-3. It defines:

- backend-owned `GET /api/finance/accounting-periods/{period}/close-checks`;
- persistent `POST /api/finance/accounting-periods/{period}/close`;
- canonical closed-period mutation error `CLOSED_ACCOUNTING_PERIOD`;
- required source mutation guard behavior for direct API calls.

Current status remains `contract_draft_only`: local framework-agnostic contract
and permission-scope tests exist under `apps/api`, but no real backend HTTP
route, database migration, auth middleware, CI evidence, release evidence, or
production implementation evidence exists in this repository.
