# Finance Bank Reconciliation API/Data Contract

Status: `backend_contract_draft`.

This document defines the backend-facing contract for bank-statement import,
cash-flow review, and bank reconciliation before API/database implementation.
It is not a production database migration, authorization policy, bank API
integration, or accounting-voucher implementation.

## 1. Scope

In scope:

- Imported bank statement rows.
- System cash-flow rows generated by receivable/payable settlement,
  employee collection, reimbursement payment, and manual bank-side supplement.
- Many-to-one bank reconciliation links where one bank statement can reconcile
  against an original system cash-flow row plus adjustment rows.
- Cash-flow review events that make a system row eligible for bank
  reconciliation.
- Audit events for import, matching, adjustment, review, confirmation, reversal,
  return, and void operations.

Out of scope:

- Direct online payment.
- Direct bank API transaction pull.
- Accounting voucher posting.
- Production ledger closing.
- Tax filing submission.

## 2. Source Of Truth

| Business fact | Owner | Rule |
| --- | --- | --- |
| Real bank movement | Bank statement import | Imported from bank statement file or future bank API. |
| System cash-flow row | `finance_transaction` | Created by upstream business or bank-side supplement, then reviewed in `流水复核`. |
| Voucher completeness | `finance_transaction` review flow | Voucher is required before review can post a cash-flow row. |
| Bank reconciliation relationship | `finance_bank_reconciliation_link` | Links one bank statement row to one or more reviewed system cash-flow rows. |
| Reconciled state | Bank reconciliation confirmation | Confirmation writes reconciliation state to the bank row and all active linked reviewed system rows. |
| Amount correction | Adjustment system cash-flow row | Original reviewed cash-flow amount is not mutated; a supplement/reversal/difference row is created and reviewed. |

## 3. Data Entities

### 3.1 `finance_bank_statement`

Imported bank statement row.

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Internal id. |
| `bank_statement_no` | yes | Bank-provided serial number or normalized statement row id. |
| `public_account_id` | yes | Matched company public account. |
| `public_account_snapshot` | yes | Account holder, bank name, tail number, and display name snapshot from import time. |
| `imported_account_name` | yes | Raw account name from the bank file; evidence only, not the account identity. |
| `statement_date` | yes | Actual bank transaction date. |
| `direction` | yes | `收入` or `支出` from bank perspective. |
| `amount` | yes | Positive amount from the bank statement. |
| `counterparty_name` | yes | Bank statement counterparty. |
| `summary` | yes | Bank statement summary or memo. |
| `balance_after` | no | Bank balance after this row if supplied by bank file. |
| `import_batch_id` | yes | Import batch id. |
| `import_status` | yes | `可入池`, `跳过`, or `异常`. |
| `match_status` | yes | Current bank reconciliation status; see state rules below. |
| `confirmed_at` | no | Reconciliation confirmation time. |
| `confirmed_by` | no | Reconciliation confirmer account id/name snapshot. |
| `created_at` | yes | Import write time. |
| `updated_at` | yes | Latest status update time. |

Unique key:

`public_account_id + bank_statement_no`

Duplicate import rows with the same key must be skipped, not inserted again.

Account rules:

- Import preview and commit must receive an explicit `public_account_id`.
- The account must be enabled and must include the `银行对账` capability.
- If the account is disabled, missing, or capability-mismatched, the import is
  blocked. The system must not fall back to a static seed account or another
  default account.
- Historical bank rows keep their stored `public_account_snapshot`; later
  account configuration edits must not rewrite imported row history.

### 3.2 `finance_transaction`

System cash-flow row. This contract references the existing finance transaction
concept instead of creating a separate table.

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Internal id. |
| `transaction_no` | yes | Business-facing cash-flow number. |
| `direction` | yes | `收入` or `支出` from company public-account perspective. |
| `amount` | yes | Positive cash-flow amount. |
| `occurred_date` | yes | Actual cash-flow occurrence date entered by business or finance. |
| `finance_period` | yes | Accounting period, formatted as `YYYY-MM`. |
| `public_account_id` | yes | Company account affected by the row. |
| `first_category_id` | yes | Finance first-level category. |
| `second_category_id` | yes | Finance second-level category. |
| `report_group` | yes | Reporting aggregation snapshot from finance category config. |
| `payment_method` | yes | Public-account payment/collection method. |
| `source_type` | yes | Business source type, for example reimbursement, collection, receivable/payable settlement, bank-side supplement, or amount adjustment. |
| `source_no` | yes | Business source number. |
| `source_description` | yes | Compact source description. |
| `review_status` | yes | `待复核`, `退回修改`, `已入账`, or `已作废`. |
| `voucher_status` | yes | `待补充` or `已上传`. |
| `reconciliation_status` | yes | `未对账`, `已对账`, or `对账异常`. |
| `created_by` | yes | Creator account id/name snapshot. |
| `reviewed_at` | no | Review posting time. |
| `reviewed_by` | no | Review operator account id/name snapshot. |

Rules:

- Only `已入账` rows can be confirmed in bank reconciliation.
- `待复核` adjustment rows can block a bank statement but cannot be confirmed.
- Original reviewed row amounts must not be edited for bank amount differences.
- A cash-flow row can only have one active confirmed bank statement relation.

### 3.3 `finance_bank_reconciliation_link`

Relationship table between bank statement rows and system cash-flow rows.

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Internal id. |
| `bank_statement_id` | yes | Related bank statement row. |
| `finance_transaction_id` | yes | Related system cash-flow row. |
| `role` | yes | `primary` or `adjustment`. |
| `relation_source` | yes | `auto_match`, `manual_confirm`, `bank_generated_flow`, or `amount_adjustment`. |
| `status` | yes | `active` or `removed`. |
| `created_at` | yes | Relation creation time. |
| `created_by` | yes | Operator or system actor snapshot. |
| `removed_at` | no | Relation removal time. |
| `removed_by` | no | Operator snapshot for removal. |
| `note` | no | Compact operation note. |

Relationship rules:

- One bank statement can have multiple active links.
- The first active `primary` link is the display anchor for the bank row.
- Additional `adjustment` links represent reviewed correction rows for the same
  bank statement.
- The sum of signed amounts of all active linked `已入账` system rows must equal
  the signed bank amount before reconciliation can be confirmed.
- If any active linked adjustment row is still `待复核`, the bank row is blocked
  as `暂不可对账`.
- Removed links are retained for audit and cannot be physically deleted in
  production.

### 3.4 `finance_reconciliation_event`

Domain event table for reconciliation lifecycle.

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Internal id. |
| `event_type` | yes | `imported`, `matched`, `system_flow_created`, `adjustment_created`, `review_posted`, `confirmed`, `reversed`, `returned`, or `voided`. |
| `bank_statement_id` | no | Related bank row when applicable. |
| `finance_transaction_id` | no | Related system row when applicable. |
| `reconciliation_link_id` | no | Related link row when applicable. |
| `before_state` | no | Compact JSON state before change. |
| `after_state` | no | Compact JSON state after change. |
| `reason` | no | Required for return, void, and reversal. |
| `created_at` | yes | Event time. |
| `created_by` | yes | Actor id/name snapshot. |

### 3.5 `audit_event`

The general audit stream must record all mutating operations in this contract.

Minimum audit fields:

- `id`
- `actor_id`
- `actor_name`
- `operation`
- `target_type`
- `target_id`
- `before_snapshot`
- `after_snapshot`
- `reason`
- `idempotency_key`
- `created_at`

## 4. State Model

### 4.1 Bank Statement Match Status

Stored status values:

| Status | Meaning |
| --- | --- |
| `银行未匹配` | Imported bank row has no usable system cash-flow row. |
| `系统未匹配` | System row exists but no bank row has been imported yet. |
| `金额不一致` | Bank row and linked reviewed system rows do not offset to zero. |
| `暂不可对账` | A required linked system row exists but is not `已入账`. |
| `待确认` | Linked reviewed system rows offset bank amount and can be confirmed. |
| `已对账` | Bank row and active linked reviewed system rows are confirmed. |
| `重复导入` | Import preview duplicate; skipped, not active reconciliation work. |

UI may group these into compact visible states such as `待处理`, `待确认`,
`异常`, and `已对账`, but API must preserve the detailed reason.

### 4.2 Cash-Flow Review Status

| Status | Meaning |
| --- | --- |
| `待复核` | Created but not posted. |
| `退回修改` | Returned to source owner for correction. |
| `已入账` | Reviewed and eligible for bank reconciliation. |
| `已作废` | Voided before posting or after allowed void flow. |

### 4.3 Cash-Flow Reconciliation Status

| Status | Meaning |
| --- | --- |
| `未对账` | Reviewed row has not been bank-reconciled. |
| `已对账` | Reviewed row is confirmed against a bank statement. |
| `对账异常` | Row is involved in an unresolved mismatch or reversal. |

## 5. Amount-Difference Flow

1. A bank statement row is imported.
2. Auto/manual matching finds a primary system cash-flow row with the same
   direction/account but different signed amount.
3. Bank row becomes `金额不一致`.
4. Operator creates a `流水补差` system cash-flow row from bank reconciliation.
5. The adjustment row enters `流水复核` as `待复核` and is linked to the same bank
   row with role `adjustment`.
6. While the adjustment row is `待复核`, the bank row becomes `暂不可对账`.
7. After review posts the adjustment row as `已入账`, the system recomputes:

```text
bank_signed_amount - sum(active_linked_reviewed_system_signed_amounts)
```

8. If the result is `0`, the bank row becomes `待确认`.
9. Confirming reconciliation writes `已对账` to the bank row and all active linked
   reviewed system rows.
10. If the adjustment row is returned or voided, the bank row returns to
    `金额不一致`.

## 6. API Contract Draft

All mutating endpoints require authentication, authorization, idempotency key,
and audit event creation. Concrete auth/resource scopes are pending backend
design.

### 6.1 Import Preview

`POST /api/finance/bank-statement-imports/preview`

Request:

```ts
type BankStatementImportPreviewRequest = {
  publicAccountId: string;
  fileId: string;
};
```

Response:

```ts
type BankStatementImportPreviewResponse = {
  batchPreviewId: string;
  accountMatched: boolean;
  statementDateRange: { start: string; end: string };
  rows: Array<{

    statementDate: string;

    amount: number;
    counterpartyName: string;
    summary: string;

    issue?: string;
    matchedFinanceTransactionIds: string[];
  }>;
};
```

`GET /api/finance/bank-reconciliation/items`

Query:

```ts
type BankReconciliationListQuery = {
  status?: '待处理' | '待确认' | '异常' | '已对账';

```

Response item:

```

```

### 6.5 Create Bank-Side System Flow

`POST /api/finance/bank-reconciliation/items/{bankStatementId}/system-flows`

Creates a system cash-flow row from a bank row that has no usable system row.
The row enters `流水复核` and does not bypass review.

### 6.6 Create Amount Adjustment

`POST /api/finance/bank-reconciliation/items/{bankStatementId}/amount-adjustments`

Request:

```ts
type CreateAmountAdjustmentRequest = {
  primaryFinanceTransactionId: string;
  adjustmentDirection: '收入' | '支出';
  adjustmentAmount: number;
  reason: string;
};
```

Rules:

- `adjustmentAmount` must equal the absolute remaining signed difference unless
  a future approved exception allows partial adjustment.
- If an active pending adjustment already exists for the same bank statement,
  creating another adjustment is blocked.
- The created row enters `流水复核` as `待复核`.

### 6.7 Confirm Reconciliation

`POST /api/finance/bank-reconciliation/items/{bankStatementId}/confirm`

Rules:

- Bank row must be `待确认`.
- All active linked system rows must be `已入账`.
- Signed bank amount must equal signed sum of active linked reviewed system rows.
- None of the active linked system rows can be reconciled to another active bank
  statement.

Effect:

- Bank row becomes `已对账`.
- Active linked system rows become `已对账`.
- A reconciliation event and audit event are written.

### 6.8 Reverse Reconciliation

`POST /api/finance/bank-reconciliation/items/{bankStatementId}/reverse`

Request:

```ts
type ReverseReconciliationRequest = {
  reason: string;
};
```

Rules:

- Reason is required.
- Reversal after period close requires a separate production governance decision.
- Reversal removes active confirmed reconciliation state but must keep historical
  relationship/event rows.

## 7. Validation Rules

- Import cannot insert rows with unknown public account, missing required bank
  fields, invalid amount, or invalid direction.
- Import cannot insert rows when the selected public account is disabled or does
  not support bank reconciliation.
- Duplicate bank rows are skipped through the unique key, not inserted.
- Reconciliation confirmation cannot proceed while any linked row is `待复核`,
  `退回修改`, or `已作废`.
- Bank statement date and system occurrence/accounting period can differ; bank
  reconciliation is not filtered by month. The pending pool is driven by
  unreconciled reviewed system rows and imported bank statement rows.
- Voucher upload belongs to cash-flow review. Bank reconciliation confirmation
  must not add a second voucher requirement when all linked system rows are
  already reviewed.
- Amount differences must be handled by correction rows, not by directly editing
  the original reviewed row.

## 8. Frontend Integration Boundary

Current frontend prototype uses `matchedTransactionIds: string[]` on bank
statement records:

- Empty array means no matched system row.
- First id is the primary display system row.
- Additional ids represent adjustment rows for the same bank statement.
- Confirmation updates the bank row plus all active linked reviewed system rows.

Backend implementation should replace this frontend-only array with the
relationship table described above. API responses may still expose
`matchedFinanceTransactionIds` as a read model for simple rendering.
