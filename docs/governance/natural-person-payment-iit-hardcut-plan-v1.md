## 1. 目标

本方案用于把项目中所有向自然人支付或返还资金的业务事实统一接入个人所得税、应付、付款、会计凭证和反向更正链路。

目标不是增加一个新的业务页面，而是建立一条跨模块领域契约，避免出现以下漂移：

- 全职工资进入个税，但兼职任务结算只作为外协付款处理。
- 绩效既并入薪酬，又独立生成绩效应付和付款。
- 报销因为没有进入薪酬而被静默排除，却没有保存不计税依据。
- 已入账自然人付款缺少对应所得记录时，申报准备仍可确认。
- 付款冲正后，应付、个税申报和会计分录无法一起回退。

本方案以当前前端 Mock 和会话状态为实施范围。正式后端持久化、事务、幂等、权限和申报接口仍按后续后端契约执行。

## 2. 已确认决策

以下决策为本轮硬切的固定输入，不再保留兼容分支：

1. 兼职合作协议金额统一为税前金额。
2. 全职员工的月度、季度绩效统一进入薪酬，薪酬是唯一支付入口。
3. 报销按费用真实性、凭证合规性、超标准金额性质三层判断。
4. 不新增审批流、审批角色或双人复核。
5. 继续使用现有业务动作：绩效确认、薪酬确认、费用报销审核、流水复核、申报准备确认和税务办理。
6. 税务分类由业务来源和人员税务身份自动推导；只有报销审核需要在现有审核动作中拆分金额去向。
7. 当前活跃计算范围为居民个人工资薪金和居民个人普通劳务报酬。非居民个人、稿酬、特许权使用费等进入阻断，不静默套用居民劳务规则。

## 3. 公开依据与项目边界

项目实现口径参考：

- 国家税务总局公告 2018 年第 61 号：向居民个人支付工资薪金采用累计预扣法；支付劳务报酬时按次或者按月预扣预缴。`https://www.chinatax.gov.cn/n810219/n810744/n3752930/n3752974/c3963396/content.html`
- 国家税务总局关于自然人劳务报酬的 2026 年问答：支付单位是扣缴义务人，劳务报酬不超过 4,000 元时减除费用 800 元，超过 4,000 元时减除 20% 费用。`https://tianjin.chinatax.gov.cn/11200000000/0300/030005/20260129152741507.shtml`
- 国家税务总局公告 2018 年第 28 号：企业所得税税前扣除凭证遵循真实性、合法性、关联性原则，并规定发票、收款凭证及内部凭证的适用边界。`https://www.chinatax.gov.cn/chinatax/n810341/n810765/n3359382/201806/c3730094/content.html`

本方案是项目内部业务系统设计基线，不替代税务机关办理结果、专业税务判断或正式会计意见。申报和缴款结果仍以自然人电子税务局及税务回执为准。

## 4. 不增加审批流的边界

本轮不得新增以下内容：

- 自然人付款税务审批。
- 绩效付款审批。
- 报销税务二审。
- 个税双人确认。
- 会计科目人工选择审批。

现有动作中的职责调整如下：

| 现有动作 | 调整后职责 | 是否新增审批 |
| --- | --- | --- |
| 绩效确认 | 冻结绩效结果并提供给薪酬 | 否 |
| 薪酬确认 | 确认工资、绩效和计税结果 | 否 |
| 费用报销审核 | 一次拆分业务报销、转薪酬、员工承担 | 否 |
| 任务验收 | 形成可结算的兼职任务事实 | 否 |
| 流水复核 | 确认实际付款事实 | 否 |
| 申报准备确认 | 冻结当期工资薪金和劳务报酬明细 | 否 |
| 税务办理 | 登记官方申报、缴款和更正结果 | 否 |

金额拆分、税务分类和凭证完整性是数据校验，不是审批步骤。

## 5. 当前问题

### 5.1 人员与付款缺少税务身份

当前 `全职 / 兼职`、`员工 / 外协 / 供应商` 是业务关系，不是税务身份。系统不能据此区分：

- 居民个人兼职。
- 非居民个人。
- 个体工商户。
- 公司供应商。

付款记录必须引用稳定的人员或交易对手 ID，不能继续通过姓名关联人员档案。

### 5.2 兼职任务结算未进入个税

当前流程是：

```text
任务验收 -> 外协应付 -> 外协付款 -> 资金凭证
```

缺少：

```text
居民个人劳务分类 -> 税前金额 -> 预扣税额 -> 实付金额 -> 个税申报 -> 个税负债
```

### 5.3 绩效存在双支付入口

薪酬计算已经消费绩效预发金额，财务侧仍存在独立绩效应付和绩效付款，缺少同一绩效结果只能结算一次的约束。

### 5.4 报销被隐式排除

真实费用返还不是员工所得，但当前记录没有保存费用真实性、凭证合规状态和超标准部分的实际处理。`无正式票据`不能继续作为一个不区分原因的笼统选项。

### 5.5 个税申报只消费工资发放快照

已入账自然人付款没有统一进入申报候选。工资付款缺少 `SalaryPaymentRecord` 时也可能被静默遗漏。

### 5.6 会计分录不能承接劳务代扣

当前外协应付和付款按全额处理，缺少税前劳务金额、实际付款金额和代扣个税负债的拆分。

## 6. 目标领域契约

新增跨模块领域类型 `NaturalPersonPaymentFact`。它是付款和税务计算之间的内部事实，不新增用户可见主模块。

```ts
type NaturalPersonIncomeType =
  | '工资薪金'
  | '劳务报酬'
  | '费用返还';

type NaturalPersonPaymentFact = {
  id: string;
  personId: string;
  personNameSnapshot: string;
  identityNoSnapshot: string;
  residencyStatus: '居民个人' | '非居民个人' | '待确认';
  incomeType: NaturalPersonIncomeType;
  sourceModule: '薪酬明细' | '任务管理' | '费用报销审核';
  sourceId: string;
  sourceNo: string;
  settlementBatchNo: string;
  incomePeriod: string;
  taxPeriod?: string;
  grossAmount: number;
  nonTaxableReimbursementAmount: number;
  taxableIncomeAmount: number;
  withholdingTaxAmount: number;
  netPayableAmount: number;
  financeTransactionNo?: string;
  evidenceStatus: '完整' | '待补凭证' | '不适用';
  filingStatus: '待付款' | '待申报' | '已申报' | '已更正' | '已冲销';
  reversalOfFactId?: string;
  sourceHash: string;
};
```

约束：

1. `(sourceModule, sourceId, settlementBatchNo)` 唯一。
2. 所有自然人支出流水必须引用一个付款事实；员工代收客户款不属于自然人支出，明确排除。
3. `grossAmount = nonTaxableReimbursementAmount + taxableIncomeAmount` 仅适用于单一付款事实；报销拆分为报销事实和薪酬调整来源时分别保存。
4. `netPayableAmount = grossAmount - withholdingTaxAmount`。
5. `费用返还`的 `taxableIncomeAmount` 和 `withholdingTaxAmount` 必须为零。
6. 已入账付款事实不可直接覆盖；冲正生成反向事实。
7. 已进入申报准备的事实保存来源快照和哈希；来源变化必须使未办理申报准备回到待确认。
8. 非居民或税务身份待确认时不得生成最终税额和付款。

## 7. 绩效唯一支付链路

目标流程：

```text
绩效规则与明细
  -> 绩效确认结果快照
  -> 薪酬计算消费绩效结果
  -> 薪酬确认
  -> 生成唯一工资应付
  -> 实际工资付款
  -> 工资薪金付款事实
  -> 个税申报准备
```

规则：

1. 绩效模块不再生成应付、付款或独立收支流水。
2. 月度绩效进入对应薪酬月份。
3. 季度绩效进入季度结算日所在月份薪酬。
4. 薪酬明细保留基础工资、绩效、调整等构成，财务统计仍可按构成汇总，但只生成一条工资应付和一条或多条真实工资付款。
5. 每条绩效结果保存 `salarySettlementReference`；一条已确认绩效只能进入一个薪酬结算批次。
6. 薪酬未确认时，绩效变化触发重新计算。
7. 薪酬已确认但未发放时，必须撤回薪酬确认后重新计算。
8. 薪酬已发放后，绩效差额进入后续薪酬的 `绩效补发 / 绩效追回`，不修改原工资单。

硬切删除：

- 独立绩效应付生成路径。
- 独立绩效付款入口。
- 独立绩效付款 Mock。
- 以 `月度绩效`作为独立付款来源的业务分支。

## 8. 兼职劳务报酬链路

目标流程：

```text
任务验收
  -> 生成兼职结算批次
  -> 读取人员税务身份
  -> 按税前金额计算劳务报酬预扣税
  -> 生成税前应付
  -> 支付税后金额
  -> 生成劳务报酬申报明细
  -> 税务办理与缴款
```

### 8.1 结算批次

- 同一兼职人员、同一劳务项目、同一结算周期内连续取得的已验收任务合并为一个结算批次。
- 同一人员在同月承接不同劳务项目时分别形成结算批次，不得跨项目合并计税。
- 预扣计算以结算批次为单位，不能通过拆分多条付款降低预扣税额。
- 结算批次保存劳务项目 ID、任务 ID、验收金额、验收时间和协议版本。
- 结算批次金额即税前金额。

### 8.2 居民个人普通劳务计算

```text
税前金额 <= 4,000 元：
应纳税所得额 = 税前金额 - 800 元

税前金额 > 4,000 元：
应纳税所得额 = 税前金额 × 80%

预扣税额 = 应纳税所得额 × 预扣率 - 速算扣除数
实付金额 = 税前金额 - 预扣税额
```

示例：

```text
税前劳务报酬：3,200.00 元
减除费用：800.00 元
应纳税所得额：2,400.00 元
预扣率：20%
预扣个税：480.00 元
实际付款：2,720.00 元
```

### 8.3 会计分录

确认兼职任务成本：

```text
借：项目成本 / 劳务成本       3,200.00
贷：应付账款-自然人劳务       3,200.00
```

实际付款并代扣个税：

```text
借：应付账款-自然人劳务       3,200.00
贷：银行存款                   2,720.00
贷：应交税费-代扣代缴个税       480.00
```

缴纳个税：

```text
借：应交税费-代扣代缴个税       480.00
贷：银行存款                     480.00
```

现有 `2221.03` 扩展为承接工资薪金和劳务报酬代扣个税，并通过辅助核算或来源类型区分所得项目。不得把劳务个税缴款错误冲减 `2211.01 应付职工薪酬-工资`。

## 9. 报销三层判断

报销仍在现有 `费用报销审核` 中一次处理，不增加税务审核。

### 9.1 第一层：费用真实性

审核人判断是否属于员工替公司实际垫付的经营费用：

- 真实且与经营相关：进入下一层。
- 无法证明真实或属于个人消费：退回或计入员工承担。

### 9.2 第二层：凭证合规性

将原 `无正式票据` 硬切为：

- `发票`
- `财政票据或其他合法凭证`
- `小额零星收款凭证`
- `暂缺合规凭证`

处理规则：

- 合规凭证：正常报销，并保存税前扣除凭证状态。
- 小额零星收款凭证：必须记录收款方、身份证号或主体信息、支出项目、金额和内部报销单。
- 暂缺合规凭证但费用真实：可以形成报销应付，标记 `待补凭证`；汇算清缴前仍未补齐时进入企业所得税纳税调整来源。
- 只有无关截图、口头说明或无法核验的材料：不得以报销应付放行。

凭证是否支持企业所得税税前扣除，不改变真实费用返还本身是否属于员工个人所得。

### 9.3 第三层：超标准部分性质

现有一次审核提交以下金额：

```ts
type ExpenseReviewDisposition = {
  submittedAmount: number;
  businessReimbursementAmount: number;
  payrollTaxableAmount: number;
  employeeBorneAmount: number;
  evidenceStatus: '合规' | '待补凭证' | '不合规';
  exceptionReason?: string;
};
```

强校验：

```text
申报金额 = 业务报销金额 + 转薪酬计税金额 + 员工承担金额
```

去向：

| 金额去向 | 后续业务 | 个税 | 财务结果 |
| --- | --- | --- | --- |
| 业务报销 | 生成员工报销应付 | 不计入 | 费用返还应付 |
| 转薪酬计税 | 生成下期薪酬调整来源 | 工资薪金 | 不生成报销应付 |
| 员工承担 | 终止处理 | 不涉及 | 不生成财务记录 |

判断示例：

- 实际住宿 700 元，标准 500 元，因展会涨价且完成现有审核中的例外说明：700 元均可作为业务报销。
- 实际住宿 700 元，公司只承担 500 元：500 元报销，200 元员工承担。
- 公司额外给员工 200 元住宿补贴：500 元报销，200 元转薪酬计税。

## 10. 个人所得税申报准备

现有个人所得税申报准备继续作为唯一入口，不新增劳务报酬申报模块。

抽屉使用现有 Tab 组件承载：

- `申报概览`
- `所得明细`
- `操作记录`

`所得明细`内使用轻量切换展示：

- 工资薪金。
- 劳务报酬。

申报准备的数据源改为所有已实际付款且属于当期的 `NaturalPersonPaymentFact`：

- 工资薪金按员工合并当期多笔工资发放。
- 劳务报酬按自然人和结算批次展示，不与工资薪金使用同一计算公式。
- 费用返还不进入应税明细，但必须能够从付款事实回查到不计税分类。
- 已入账自然人支出缺少付款事实、税务身份或所得分类时，申报准备必须阻断。
- 工资付款流水缺少薪酬发放快照时必须计入待处理，不允许静默忽略。
- 申报确认冻结当期工资薪金和劳务报酬来源快照。

## 11. 反向与更正链路

### 11.1 付款未申报

- 付款冲正生成反向付款事实。
- 应付结算金额按已入账付款及冲正净额重新推导。
- 个税申报准备重新计算并回到待确认。

### 11.2 已确认准备但未进入办理

- 来源事实变化使准备记录失效。
- 用户重新确认现有申报准备，不新增审批。

### 11.3 已进入税务办理或已申报

- 不覆盖原申报快照。
- 使用现有税务办理更正路径生成更正版本。
- 更正版本引用原付款事实和冲正事实。

### 11.4 绩效和报销反向

- 已发放绩效差额进入后续薪酬调整。
- 已付款报销发生退回时，生成付款冲正和报销应付回退。
- 已转薪酬的报销金额在薪酬未发放时可撤回；已发放后通过后续薪酬调整处理。

## 12. 前端页面调整

### 12.1 人员档案

不新增业务人员可选的“所得类型”字段。增加系统使用的税务身份事实：

- 居民身份状态。
- 证件信息完整性。
- 自然人报送状态。

兼职默认形成劳务报酬候选，但最终由人员税务身份决定是否可计算。

### 12.2 绩效明细

- 只展示绩效结果和薪酬承接状态。
- 去掉独立支付语义。
- 已进入薪酬时显示对应薪酬月份和薪酬单号。

### 12.3 薪酬明细

- 保留绩效构成。
- 展示绩效来源快照。
- 一次确认工资、绩效和个税。

### 12.4 费用与代收 / 费用报销审核

- 费用提交人仍只提交真实费用和凭证，不要求提交人判断个税。
- 报销审核抽屉增加金额去向拆分，不增加 Tab 和审批步骤。
- 代收登记保持排除：它是客户资金转入公司，不是公司向员工支付所得。

### 12.5 应收应付

- 工资只显示统一薪酬应付。
- 兼职显示税前应付金额、代扣税额和待实付金额。
- 报销只显示批准的业务报销金额。
- 不提供税务分类编辑入口。

### 12.6 收支流水

- 自然人付款显示税前来源金额、代扣税额和实际付款金额。
- 列表保持克制，详细拆分放在现有抽屉。
- 所有自然人支出使用人员 ID 或交易对手 ID，不再按姓名关联。

### 12.7 会计凭证

- 工资、劳务、报销分别按来源映射科目。
- 劳务付款凭证必须拆分银行实付和代扣个税。

## 17. 完成定义

只有同时满足以下条件，才能称为前端自然人付款与个税链路闭环：

1. 所有自然人支出都能追溯到稳定人员 ID、业务来源和所得分类。
2. 全职绩效不存在独立付款路径。
3. 兼职税前金额、代扣个税和实付金额能够对平。
4. 报销不计税有明确的费用真实性和金额去向依据。
5. 已入账自然人付款无法被申报准备静默遗漏。
6. 个人所得税准备同时覆盖工资薪金和劳务报酬。
7. 个税申报、付款和会计分录金额一致。
8. 冲正和更正不覆盖原始事实，且能够完整反向。
9. Mock 数据不存在人员缺失、名称关联、重复结算或孤立来源。
10. 类型检查、单测、构建、治理检查和浏览器验收均有证据。
