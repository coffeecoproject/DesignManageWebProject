## 1. 文档目的

本方案用于补齐当前前端缺失的客户任务收入链路，将不同品牌下的施工图、平面方案、门店 P 图等任务，从品牌计价配置一直追溯到财务应收：

```text
客户合同
  -> 品牌任务计价配置
  -> 任务创建时冻结计价快照
  -> 内部验收形成任务结算事实
  -> 按任务或按月形成客户应收
  -> 发票关联
  -> 收款流水
  -> 会计凭证
  -> 总账、期间结账和财务报表
```

本方案是前端结构性硬切，不是新增审批系统，也不是后端、数据库或生产财务实施方案。它解决当前前端中“品牌可选任务没有客户价格、任务验收没有收入事实、财务应收依赖静态 Mock”的跨模块漂移。

## 2. 范围边界

### 2.1 本轮纳入

1. 品牌级结算规则和品牌任务计价版本。
2. 品牌管理抽屉中的任务计价配置 UI。
3. 任务创建时自动解析并冻结客户计价快照。
4. 内部验收时原子生成任务结算事实。
5. 按任务结算和按自然月汇总结算的前端派生模型。
6. 任务结算事实到财务应收应付的来源适配。
7. `应收应付`对`任务结算`来源的详情和追溯展示。
8. 任务金额的前端可见性边界。
9. Mock、领域测试、跨模块验收矩阵、路由页面契约和证据文档。
10. 品牌单一验收配置、任务创建快照和任务详情中的甲方验收录入与更正审计。

1. 后端 API、DTO、数据库表、迁移、持久化、事务、并发、唯一索引和消息投递。

7. 按面积、按工时、阶梯价、套餐拆分、折扣引擎和多币种。
8. 修改发票、收款、凭证、总账、期间结账和报表自身的既有业务流程。
9. 浏览器刷新后的持久化和正式审计日志。

### 2.3 前端原型边界

本轮完成后可以证明：

- 同一前端会话内，品牌配置、任务创建、内部验收和财务应收读取同一份领域事实。
- 正向链路、阻断规则、历史冻结和来源追溯可以通过 Mock 和自动测试验证。
- 页面不会把客户结算金额暴露给员工任务视图。

本轮不能证明：

- 刷新后数据仍然存在。
- 多用户并发下不会重复生成应收。
- 后端权限、数据库唯一约束和操作审计已经实施。
- 真实财务数据已经接入或具备生产审计能力。

## 3. 已确认业务决策

以下决策是本轮硬切固定输入，不保留旧分支：

1. 同一任务类型可以因品牌不同而使用不同客户结算价格。
2. 客户计价和员工绩效、全职薪酬、兼职劳务应付是独立规则族，不得共用金额。
3. 内部验收只形成`待甲方验收`客户结算事实；录入甲方评分与时效结果后，系统按冻结规则计算净额并形成应收。
4. 甲方反馈继续用于反馈归档，与甲方验收评分、时效及结算扣款相互独立。
5. 品牌管理负责配置任务是否计费、结算单价、价格依据合同和结算周期。
6. 合同管理 UI 保持不变。合同只作为品牌价格的数据依据，不成为第二个价格编辑入口。
7. 员工任务 UI 不展示客户价格和应收关系；管理端任务详情增加轻量甲方验收页签，仅展示标准金额、规则计算过程和最终结算金额。
8. 不新增任务结算页面。任务结算结果由现有`应收应付`页面承接。
9. 按任务结算：每条完成内部验收、甲方验收且可计费的任务形成一条已确认来源应收。
10. 按月汇总：同一结算主体、品牌、合同、甲方验收归属月份的有效任务先形成结算事实，自然月结束后自动冻结汇总并形成一条已确认来源应收。
11. 计费任务必须有当前有效的品牌任务价格和价格依据合同；缺失时不得静默按 0 元生成应收。
12. 不计费任务不生成应收，但保留“不计费”结算事实以支持追溯。
13. 修改品牌价格自动形成新版本，不覆盖历史版本；不提供人工价格版本管理页面。
14. 任务创建时冻结价格、合同、结算规则和验收规则快照。后续改价、改验收规则、换合同或合同到期不改变历史任务。
15. 返工不重复计费；任务只有一次有效内部验收结算事实。
16. 已中止任务不生成有效应收。
17. 已形成应收或已记账来源不得被品牌改价反向覆盖，只能走财务既有调整、冲销或补差口径。
18. 固定金额合同的额度仅用于管理提醒；超额不阻断任务创建、验收或应收生成，无固定金额合同不计算额度状态。
19. 一条兼职任务可以同时形成客户应收和自然人劳务应付，两者金额和生命周期互不替代。
20. 发票不是任务收入生成前提。发票继续在应收形成后按现有多对多关联流程处理。

## 4. 当前代码审查结论

### 4.1 品牌任务配置只有任务选择

`BrandTaskConfigRecord`当前只有`id`和`taskConfigId`。品牌抽屉的`任务与绩效`只支持从已发布绩效规则中添加或移除适用任务，并展示绩效分值，没有：

- 是否计费。
- 客户结算单价。
- 价格依据合同。
- 价格版本。
- 结算方式和到期规则。

因此当前品牌任务配置只能回答“这个品牌能创建什么任务”，不能回答“该任务验收后形成多少客户应收”。

### 4.2 合同模型已有可复用依据，不需要扩展 UI

`CustomerContractRecord`已经包含：

- 客户归属。
- 合同类型。
- 固定金额或无固定金额。
- 合同金额。
- 签署日期和到期日期。
- 合同文件。
- 价税口径和合同业务性质。

这些字段足以作为首版品牌任务价格依据。品牌页只允许选择所属客户的有效合同；合同页无需增加适用品牌、计价关联或任务价格维护 UI。

### 4.3 任务没有客户计价快照

`StoreTaskRecord`当前保存客户、品牌、门店、任务类型、执行人、验收人和任务生命周期。唯一金额字段是兼职执行人的`laborAgreement.agreedGrossAmount`，该字段属于员工侧劳务应付，不是客户收入。

任务创建和任务验收当前没有：

- 品牌计价版本引用。
- 合同引用。
- 客户价格快照。
- 结算方式快照。
- 任务结算事实。

### 4.4 验收提交原有缺口

实施前的`applyTaskAcceptanceCommit`只原子更新：

- 任务记录。
- 任务绩效评分记录。
- 兼职劳务验收记录。

客户任务结算事实当时尚未进入同一次前端领域提交，因此任务显示已完成后没有稳定收入来源。本轮已按统一政策改为：内部验收同时形成稳定验收归档、任务绩效和客户任务结算事实；兼职劳务资料不完整时仅保留劳务阻断，不回滚客户收入事实。

### 4.5 财务已有来源适配模式

`FinanceManagementProvider`已经通过适配器把：

- 兼职劳务结算批次合并为应付。
- 薪酬结果合并为应付。

`应收应付`已经支持确认、收付款、发票关联、凭证生成、期间锁定和后续追溯。本轮应复用同一模式增加客户任务结算适配，不复制一套财务状态。

### 4.6 当前应收来源没有任务结算

`FinanceReceivablePayableSourceType`当前包含合同应收、项目阶段确认、薪酬发放、员工报销、外协结算等类型，但没有`任务结算`。现有部分客户收入是静态 Mock，无法追溯到任务验收和品牌价格。

## 5. 目标前端领域边界

### 5.1 单一事实关系

```text
CustomerManagementState
  -> 客户、合同、品牌、品牌结算规则、品牌任务价格版本

TaskManagementState
  -> 任务、任务客户计价快照、内部验收、任务结算事实

FinanceManagementState
  -> 任务结算批次适配、应收应付、发票、流水、凭证及账簿消费者
```

Provider 依赖方向保持：

```text
CustomerManagementProvider
  -> TaskManagementProvider
  -> FinanceManagementProvider
```

不允许财务页面反向修改品牌价格，不允许品牌页面直接写财务应收，不允许任务页面维护第二份合同或价格表。

### 5.2 状态所有权

| 事实 | 唯一所有者 | 允许消费者 |
| --- | --- | --- |
| 客户和合同档案 | `CustomerManagementState` | 品牌计价、财务税务只读消费 |
| 品牌结算规则 | `CustomerManagementState` | 任务创建、任务结算派生 |
| 品牌任务价格版本 | `CustomerManagementState` | 任务创建时解析并冻结 |
| 任务客户计价快照 | `TaskManagementState` | 验收和追溯，不进入员工视图模型 |
| 任务结算事实 | `TaskManagementState` | 财务来源适配 |
| 客户任务结算批次 | 任务结算领域模型派生 | `FinanceManagementState` |
| 应收及后续财务状态 | `FinanceManagementState` | 发票、流水、凭证、总账和报表 |

## 6. 目标领域模型

以下类型约束前端内部状态，不代表后端 API 或数据库已经实施。

### 6.1 品牌结算规则

```ts
type BrandSettlementMode = '按任务结算' | '按月汇总';

type BrandSettlementPolicy = {
  brandId: string;
  mode: BrandSettlementMode;
  perTaskDueDays?: number;
  monthlyDueDay?: number;
};
```

规则：

- `按任务结算`使用`验收日期 + perTaskDueDays`形成应收到期日。
- `按月汇总`按自然月归集，使用次月`monthlyDueDay`形成应收到期日。
- 首版不增加任意账期表达式、季度结算和自定义截账日。

### 6.2 品牌任务价格版本

```ts
type BrandTaskPricingVersion = {
  id: string;
  brandId: string;
  taskConfigId: string;
  billable: boolean;
  unitPrice: number;
  currency: 'CNY';
  contractId?: string;
  version: number;
  effectiveFrom: string;
  effectiveTo?: string;
  status: '生效中' | '已失效';
  createdAt: string;
};
```

规则：

1. 同一品牌、任务类型、时间点最多有一个生效版本。
2. `billable=true`时单价必须大于 0 且必须关联有效合同。
3. `billable=false`时单价固定为 0，不生成应收。
4. 编辑已生效价格时关闭旧版本并创建新版本，不修改旧对象。
5. 合同候选仅来自品牌所属客户，且在新版本生效日处于有效期内。
6. 价格版本冻结合同的价税口径快照，后续合同资料变化不反向改写历史任务。

### 6.3 任务客户计价快照

```ts
type TaskCustomerBillingSnapshot = {
  pricingVersionId: string;
  brandId: string;
  customerId: string;
  taskConfigId: string;
  billable: boolean;
  unitPrice: number;
  quantity: 1;
  amount: number;
  currency: 'CNY';
  contractId?: string;
  contractCodeSnapshot?: string;
  contractNameSnapshot?: string;
  contractAmountModeSnapshot?: '固定金额' | '无固定金额';
  contractAmountTaxModeSnapshot?: string;
  settlementMode: BrandSettlementMode;
  perTaskDueDays?: number;
  monthlyDueDay?: number;
  frozenAt: string;
};
```

该快照在任务创建时生成并写入任务领域状态，但不进入任何员工任务页面的视图模型或组件属性。

### 6.4 任务结算事实

```ts
type CustomerTaskBillingFactStatus = '有效' | '不计费' | '已冲销';

type CustomerTaskBillingFact = {
  id: string;
  taskId: string;
  taskNo: string;
  taskNameSnapshot: string;
  customerId: string;
  customerNameSnapshot: string;
  brandId: string;
  brandNameSnapshot: string;
  storeId: string;
  storeNameSnapshot: string;
  acceptedAt: string;
  acceptedBy: string;
  accountingPeriod: string;
  billingSnapshot: TaskCustomerBillingSnapshot;
  amount: number;
  status: CustomerTaskBillingFactStatus;
  createdAt: string;
};
```

规则：

- `id`由任务 ID 稳定派生。
- 一个任务最多存在一条当前有效结算事实。
- 返工不会新增结算事实。
- 不计费任务保留金额为 0 的事实，但财务适配器忽略该事实。
- 已经形成应收后，任务结算事实不得被品牌改价覆盖。

### 6.5 客户任务结算批次

```ts
type CustomerTaskSettlementBatch = {
  id: string;
  batchKey: string;
  customerId: string;
  customerNameSnapshot: string;
  brandId: string;
  brandNameSnapshot: string;
  contractId: string;
  contractCodeSnapshot: string;
  settlementMode: BrandSettlementMode;
  accountingPeriod: string;
  confirmDate: string;
  dueDate: string;
  amount: number;
  sourceFactIds: string[];
  sources: CustomerTaskBillingFact[];
};
```

批次键：

- 按任务：`task-revenue:{taskId}`。
- 按月：`task-revenue:{period}:{customerId}:{brandId}:{contractId}`。

同一批次只能生成一条来源应收。按月模式在自然月结束前只累计任务结算事实，不提前生成应收；自然月结束后首次派生时生成已确认应收。来源应收尚未被发票、收付款、凭证或锁期消费时，甲方验收更正和迟到事实可以直接重算；已有财务后续时不得覆盖原应收或自动生成第二条应收，必须进入冲销或后续调整口径。

## 7. 目标业务流程

### 7.1 品牌配置

```text
选择所属客户
  -> 选择绩效规则和适用任务
  -> 配置品牌结算方式
  -> 为每项任务设置是否计费、单价和依据合同
  -> 保存时校验合同、价格和有效性
  -> 已有生效价格的修改自动形成新版本
```

### 7.2 任务创建

```text
选择品牌和任务类型
  -> 系统查找当前生效价格版本
  -> 校验品牌、任务、合同和结算规则
  -> 冻结客户计价快照
  -> 创建任务
```

计费任务缺少有效价格时禁止创建，不允许使用 0 元、最近一版或任意品牌价格静默兜底。不计费任务允许创建并冻结不计费快照。

### 7.3 内部验收

```text
任务提交
  -> 内部验收通过
  -> 同一次前端领域提交写入：
       已完成任务
       绩效评分事实
       兼职劳务验收事实（适用时）
       客户任务结算事实
```

客户结算事实生成失败时，不得出现“任务已完成但收入事实静默丢失”。前端提交函数返回明确阻断结果，页面继续使用现有验收错误反馈区域，不增加审批状态或金额字段。

### 7.4 应收生成

```text
有效任务结算事实
  -> 按品牌规则形成单项或月度结算批次
  -> FinanceManagementProvider 来源适配
  -> 生成已确认任务应收
  -> 财务在现有应收应付流程只读承接
```

`应收应付`不增加确认任务应收的动作：

- 按任务模式的上游确认事实就是内部验收。
- 按月模式的上游确认事实是自然月结束后自动冻结的任务结算批次。
- 财务页面不重复确认收入事实，只继续承接收付款、发票关联和后续账务流程。

生成的应收使用：

- `direction = 应收`
- `counterpartyType = 客户`
- `counterpartyId = customerId`
- `sourceType = 任务结算`
- `sourceNo = batch.id`
- `sourceTitle = 品牌 + 期间/任务 + 任务结算`
- 收入类目使用设计服务收入的权责类目，不再把应收来源类目命名为客户回款。

`客户回款`继续只用于真实收款流水，不与收入确认类目混用。

### 7.5 后续财务链路

```text
任务应收确认
  -> 权责凭证候选
  -> 发票台账多对多关联
  -> 收款登记和流水复核
  -> 资金凭证
  -> 总账、期间结账和报表
```

本轮只验证新`任务结算`来源能够被既有下游消费，不重构这些页面。

## 8. UI 方案

### 8.1 品牌管理是唯一新增配置 UI

现有品牌抽屉继续保持两个顶层 Tab：

1. `品牌资料`
2. `任务配置`，由现有`任务与绩效`更名

`任务配置`包含三个垂直区块，不再拆分更多 Tab：

1. `绩效规则`：保持现有规则选择和只读摘要。
2. `结算规则`：选择按任务或按月汇总，并填写对应到期参数。
3. `适用任务`：在现有任务表中增加是否计费、结算单价和价格依据合同。

维护态任务表字段：

| 字段 | 说明 |
| --- | --- |
| 任务类型 | 继续来自全局任务配置和品牌绩效规则交集 |
| 绩效分值 | 只读，继续来自绩效规则 |
| 是否计费 | 二元开关；关闭时清空并禁用价格 |
| 结算单价 | 人民币元/项，最多两位小数 |
| 价格依据 | 选择品牌所属客户的有效合同 |
| 操作 | 只保留现有移除操作 |

只读态展示同样字段，但不展示内部版本 ID、生效结束时间、哈希、来源键或系统事件。

## 10. 合同、价格和历史控制

### 10.1 有效合同选择

品牌价格只能引用：

- `contract.customerId === brand.customerId`。
- 价格生效日不早于合同签署日。
- 价格生效日不晚于合同到期日。
- 合同具有已上传的签署文件。

### 10.2 固定金额合同额度

固定金额合同额度计算：

```text
已结算金额 = 当前有效已验收计费事实金额合计
剩余额度 = max(0, 合同金额 - 已结算金额)
超出金额 = max(0, 已结算金额 - 合同金额)
```

使用率达到 `80%` 时标记“接近上限”，达到或超过 `100%` 时标记“已超出”。额度不使用进行中任务的预占金额，不阻断正向业务，不新增超额审批或人工放行。已形成应收的历史事实不得因为合同金额被后改而消失。

额度台账以品牌当前计费配置关联的固定金额合同为主记录；即使尚无验收事实，也必须展示合同金额、`0` 已结算和完整剩余额度。有效已验收计费事实只负责累计已结算金额，不能决定合同台账记录是否存在。

### 10.3 历史快照

以下变化不得修改历史任务和应收：

- 品牌改价。
- 品牌更换绩效规则。
- 合同到期。
- 合同名称修改。
- 客户或品牌名称修改。
- 结算方式从按任务改为按月或反向修改。

历史任务和应收读取自己的冻结快照，主数据只用于当前和未来配置。

| 场景 | 前端处理 |
| --- | --- |

## 13. Mock 数据方案

Mock 必须形成自洽的真实样例，不保留“已关联但无来源”等矛盾数据。

至少覆盖：

1. 同一任务类型在两个品牌下价格不同。
2. 同一品牌的全套施工图、平面方案和 P 图分别为计费、计费和不计费。
3. 年框无固定金额合同下按月汇总。
4. 项目固定金额合同下按任务结算。
5. 品牌价格修改前后各创建一条任务，历史价格不同且稳定。
6. 一条全职任务只生成客户应收和绩效来源。
7. 一条兼职任务同时生成客户应收和劳务应付。
8. 一条不计费任务完成后无应收。
9. 一条返工后再次验收的任务仍只有一条有效应收来源。
10. 一个月内多条任务汇总为一条应收，并能展开来源任务。
11. 固定合同达到 `80%` 和超过合同金额的软提醒样例，并验证应收不被截断。
12. 已确认或已记账应收不受品牌改价影响。

现有以`项目阶段确认`模拟任务收入的数据应迁移为真实任务结算来源；非任务项目阶段收入可以保留，不得通过兼容别名伪装为新来源。

## 20. 当前阻断与后续边界

### 20.1 当前实施阻断项

合同 UI、管理端任务甲方验收、员工金额可见性、财务承接和合同额度边界已经确认；当前无前端实施阻断项。

### 20.2 实施时必须停止确认的情况

- 需要新增任务结算页面或人工结算审批。
- 需要在任务页面展示客户金额。
- 需要修改合同管理 UI。
- 需要引入报价单、套餐价、面积价或多币种。
- 需要真实后端、数据库、权限或生产财务数据。
- 需要把甲方验收升级为审批流，或改变为内部验收直接形成应收。

### 20.3 剩余风险

1. 前端会话状态无法提供跨刷新、并发和正式审计保证。
2. 合同额度是基于前端会话中已验收计费事实的管理提醒；后端接入后需由服务端汇总真实事实，但仍不升级为强阻断。
3. 自动应收的正式幂等必须由数据库唯一约束和服务端事务实现。
4. 前端金额不可见不等于后端字段级授权。
5. 月度来源更正已按“未消费直接重算、已消费进入财务调整阻断”处理；正式环境仍需要后端会计期间契约、唯一约束和事务承接。

## 21. 完成定义

本轮前端实施只有同时满足以下条件才能声明完成：

1. 品牌计价是客户任务价格的唯一配置来源。
2. 合同和任务页面没有新增计价 UI。
3. 任务创建冻结价格、结算与验收规则；内部验收形成待验收事实，甲方验收形成净额结算事实。
4. 按任务和按月结算都能生成可追溯应收。
5. 不计费、返工、中止和重复提交均有明确结果；固定合同额度只产生管理提醒，不改变任务应收。
6. 品牌改价不改变历史任务、应收和凭证。
7. 员工任务视图不包含客户金额。
8. 新应收可以进入现有发票、收款、凭证和账簿链路。
9. TR-01 至 TR-46 均有对应自动或代码证据。
10. 所有规定自动门禁通过，并明确保留前端原型边界。

## 22. 实施结果

1. 品牌任务配置现在维护结算方式、到期规则、是否计费、当前单价和同客户有效合同；改价写入新价格版本。
2. 任务创建自动冻结客户、品牌、合同、结算规则和价格版本快照；任务及员工页面不展示这些财务字段。
3. 内部验收生成稳定的任务客户结算事实；重复验收、返工、中止和不计费任务均有确定结果。
4. 按任务及按月汇总批次均由任务事实派生，并以`任务结算`来源进入现有应收、发票关联、收款登记和权责凭证链路。
5. 应收详情可以追溯冻结的客户、品牌、合同、任务、验收时间、价格版本和结算金额。
6. 合同页面和员工任务页面没有新增计价操作；管理端任务详情仅增加甲方验收结果录入，未新增任务结算页面或审批状态。
7. 自动测试、类型检查、lint、构建、AI Native 检查、静态残留扫描和浏览器关键路径证据共同支撑本轮前端范围。
8. 统一收入政策为内部验收形成待甲方验收结算事实；甲方验收只录入评分、时效结果和备注，系统按任务冻结的品牌验收规则计算扣分、扣款率和净额后触发应收；验收归档具有稳定文件地址，并作为任务应收的冻结来源证据。
9. 兼职劳务资料阻断与客户收入解耦，不再因为员工侧资料问题回滚客户结算事实。
10. 验收撤销按财务是否已消费区分直接作废与冲销/后续调整，原始历史不被覆盖。
11. 品牌验收配置不分版本；保存后立即供新任务使用，任务创建时冻结验收规则内容，后续品牌改动不重算历史任务。价格与结算规则仍按各自版本契约管理。
12. 甲方验收不提供手工扣款金额输入；质量扣分与超时扣分累计后按冻结档位自动换算扣款，`不计时`不产生时效扣分但必须说明原因。
13. 已消费任务应收更正不再覆盖原单或生成重复应收：发票走红票、流水按复核状态进入对应页面、已结账凭证生成后续期间差额凭证；只有相关发票、流水及会计差异均处理完毕后，更正事项才关闭。
14. 来源主数据缺失保持只读异常，本期不新增跳转、审批或独立处理页面。
