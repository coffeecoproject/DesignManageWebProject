# 税务申报材料前端硬切与验收口径 v1

## 1. 目标与边界

本轮只调整前端领域合同、页面交互、Mock 数据与自动测试，不接入电子税务局，不实现服务端持久化，也不宣称系统已经能够自动核验税务机关数据。

硬切删除“填写一个申报回执号或上传一份文件即完成税务事项”的旧口径。税务申报结果、正式申报表、申报结果回执和缴款材料必须分别记录。

## 2. 材料合同

每个已申报版本独立保存：

- 实际申报日期与申报结果；
- 正式申报表，可包含多份；
- 申报结果回执，一份；
- 税务机关申报序号，可选；
- 应征凭证序号，可选；
- 核验状态、核验人、核验时间和不一致说明；
- 缴款回单、退税回单和退抵材料，继续由各自资金环节记录。

申报序号只作为查询辅助信息，不能代替正式申报表或申报结果回执。

## 3. 状态规则

申报材料状态只允许：

- `材料待补`：正式申报表或申报结果回执缺失；
- `待核验`：两类文件齐全，但尚未人工核对；
- `核验不一致`：系统记录与税务机关结果不一致，并且必须填写原因；
- `已齐全`：两类文件齐全且人工核验一致；
- `无需申报材料`：无申报义务或社保公积金事项。

税务事项的业务进度使用 `申报材料待核对` 汇总上述未完成状态。不得恢复旧 `待补回执` 状态。

## 4. 业务门禁

- 登记申报结果允许暂不上传材料，用于承接税务机关文件晚到场景。
- 选择“人工核验一致”时，正式申报表和申报结果回执必须同时存在。
- 选择“核验不一致”时，必须记录不一致原因。
- 有应缴金额时，缴款登记优先于材料归档，不因材料晚到阻断真实缴款。
- 税务事项只有资金处理完成且申报材料状态为 `已齐全` 才能进入 `已完成`。
- 权责计提凭证不依赖后续申报材料。
- 申报差额凭证必须等待当前申报版本材料核验一致；未满足时使用 `tax_declaration_evidence_pending` 阻断原因。
- 发起更正或作废时，当前版本材料进入历史快照；新版本重新从 `未核验` 开始，不能复用上一版本材料。
- 替换当前版本材料时必须移除旧版本指针对应的陈旧文件，不得同时展示两套“当前材料”。

## 5. 前端呈现

税务办理详情保留四个职责明确的页签：

- `申报结果`：办理结果、补退金额、材料状态和核验记录；
- `申报明细`：按税种展示本次申报来源；
- `申报材料`：统一使用文件预览与下载组件；
- `操作记录`：登记、更正、材料维护和资金动作的审计记录。

页面不得展示“系统已自动核验税务机关结果”等没有真实能力支撑的文案。

## 6. Mock 与验收

Mock 至少覆盖：

- 正常申报且材料核验一致；
- 零申报但材料晚到；
- 文件齐全但待核验；
- 核验不一致；
- 更正申报后新版本重新补材料；
- 替换材料后旧当前版本文件不再残留。

自动验收必须证明：

1. 单独的申报序号不能使事项完成；
2. 只有一类文件时为 `材料待补`；
3. 两类文件齐全但未核验时为 `待核验`；
4. 两类文件齐全并人工核验一致后为 `已齐全`；
5. 领域函数不能绕过上述完整性校验；
6. 申报差额凭证在材料未核验时保持待处理；
7. 权责计提凭证不被后续申报材料阻断；
8. 更正历史保留原版本材料证据。

## 7. 后端接入前保留项

- 文件上传、下载、预览和版本归档仍为前端 Mock；
- 核验人当前来自演示账号，不具备真实身份审计能力；
- 税务机关申报序号和应征凭证序号尚未通过官方接口校验；
- 正式接入后必须由服务端保证事项版本、材料版本和操作记录的原子一致性。
