## 1. 文档目的

本方案用于将当前“全职人员自动进入静态社保记录、人工确认金额、延期记录滚入下月”的前端模型，硬切为符合真实业务顺序的社保缴费链路：

```text
劳动或合作关系事实
  -> 判断本单位是否存在参保义务
  -> 办理增员、减员或停保
  -> 确定参保生效区间和缴费基数
  -> 按所属地区及所属期解析政策版本
  -> 生成月度内部测算
  -> 登记或导入官方核定结果
  -> 核对差异并确认个人、单位承担金额
  -> 薪酬消费个人承担金额
  -> 会计计提个人代扣和单位负担
  -> 完成实际缴费、流水复核和银行对账
  -> 补缴或更正保留原所属期
```

本方案是前端结构性硬切，不是后端、数据库、生产社保或第三方接口实施方案。它不替代人社、医保、税务和公积金经办系统的正式结果。

## 2. 范围边界

### 2.1 本轮纳入

1. 人员档案中的劳动关系类型、社保参保结论和办理结果。
2. 入职、离职触发的增员、停保和当月缴费待确定事项。
3. 社保、公积金共用页面壳，但使用相互独立的业务状态和政策口径。
4. 社保政策按地区、险种和生效期间解析。
5. 年度缴费基数、新入职基数和上下限校验。
6. 月度参保人员候选、内部测算、官方核定和差异处理。
7. 社保个人承担金额到薪酬、个税的唯一消费契约。
8. 单位负担、个人代扣、缴费、流水和会计凭证的前端勾稽。
9. 欠缴、补缴、更正和当月欠费注销的前端状态模型。
10. Mock、领域测试、跨模块验收矩阵和治理证据。

1. 后端 API、数据库表、迁移、持久化、事务、并发和幂等。
2. 人社、医保、税务、公积金平台的真实 API 接入。
3. 官方核定单、缴费回执的真实解析、验签和对象存储。

6. 代缴机构、劳务派遣、跨省统筹和境外人员的完整特殊规则。
7. 真实政策参数的生产维护和法务、社保顾问意见替代。
8. 浏览器刷新后的持久化和多用户同时办理。

### 2.3 前端原型证据边界

本轮完成后可以证明：

- 同一前端会话内，人员入离职、参保办理、月度核定、薪酬扣款和财务缴费读取同一份领域事实。
- 当月离职不会被前端日期规则直接判定为“不缴”。
- 历史月份不会因为当前政策变化而重算。
- 内部测算与官方核定可以形成差异并被追溯。
- 补缴和更正保留原所属月份，不伪装成下月正常缴费。

本轮不能证明：

- 官方平台已经接受增减员、核定或缴费申报。
- 刷新后办理结果仍然存在。
- 真实政策、费率、基数和滞纳金已经由官方接口持续同步。
- 后端权限、审计、唯一约束和生产数据安全已经实施。

## 3. 已确认业务决策

以下决策是本轮硬切固定输入，不保留旧兼容分支：

1. 不新增页面、路由、主导航或审批流。
2. 现有`社保公积金`页面内部提供`参保办理`和`月度缴费`两个业务视图。
3. 社保与公积金只共用页面布局和文件组件，不共用参保义务、政策、状态机或核定结果。
4. 是否应参保依据劳动关系和官方办理结果，不依据`全职 / 兼职`显示类型直接推导。
5. 项目中的独立劳务兼职默认不建立职工社保义务；若实际属于非全日制劳动关系，必须按劳动关系重新判定，不能套用独立劳务口径。
6. 用工已经开始但尚未办理增员时，状态为`待增员`，不是`无需参保`。
7. 试用期不构成不参保理由。
8. 离职日期只触发停保事项，不直接决定离职当月是否缴费。
9. 当月离职且官方生效结果未返回时，保留当月应缴候选，不允许直接标记不缴。
10. 官方确认当月无需缴纳或允许注销当月已核定欠费后，才把当月结论改为`无需缴纳`。
11. 删除自由选择的`本月不缴`和`延期补缴`。
12. 欠缴是原所属期未完成的义务；补缴保留原所属期、补缴办理期、本金和滞纳金，不滚入下月正常缴费。
13. 薪酬等待的是本期个人承担金额已核定或经现有财务职责确认，不等待实际缴费完成。
14. 实际缴费可以发生在薪酬确认之后，但期间结账继续检查本期社保公积金计提和应完成事项。
15. 内部测算不是正式应缴金额。官方核定金额或有依据的确认金额才可进入正式薪酬和会计来源。
16. 首版前端采用结构化手工登记官方结果并附核定文件，不虚构已接入官方 API。
17. 社保政策使用所属地区和所属期版本，不允许用当前版本重算历史月份。
18. 已进入已确认薪酬或已记账凭证的社保金额不得直接覆盖；差异通过后续薪酬调整、会计调整或补缴事实承接。

## 4. 真实业务依据与解释边界

### 4.1 参保登记

《中华人民共和国社会保险法》第五十八条规定，用人单位应自用工之日起三十日内为职工申请办理社会保险登记；未办理登记的，由经办机构核定应缴社会保险费。

来源：

- `https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2023/art_e81d115419b4463ebb59ec46467fb136.html`

因此，`尚未增员`是办理状态，不是免除参保义务的结论。

### 4.2 按时足额缴费

《中华人民共和国社会保险法》第六十条和第八十六条要求用人单位按时足额缴纳；欠缴情形可能产生补缴、滞纳金及进一步责任。

来源：

- `https://www.npc.gov.cn/zgrdw/npc/ztxw/tctjcxsbtxjs/2014-05/20/content_1863737.htm`

因此，系统不能把`延期`或`不缴`作为普通可选操作。

### 4.3 武汉单位缴费流程

武汉公开流程要求单位先在社保服务渠道进行缴费申报，生成单位和个人应缴数据，再按要求完成缴费。

来源：

- `https://www.wuhan.gov.cn/zwgk/xxgk/zcwd/202408/t20240829_2447540.shtml`
- `https://rsj.wuhan.gov.cn/wechat/rdwt/202311/t20231102_2292750.html`

因此，内部测算、官方核定和实际缴费必须是三个不同事实。

### 4.4 缴费工资和基数区间

武汉年度申报以职工上年度月平均工资为主要依据；无上年度完整工资的人员需要按适用规则确定新入职基数。湖北公布的缴费基数上下限必须按所属政策期间处理。

来源：

- `https://rsj.wuhan.gov.cn/zwgk_17/zc/qtzdgknr/tzgsgg/202403/t20240315_2372942.html`
- `https://rst.hubei.gov.cn/zfxxgk/zc/qtzdgkwj/202509/t20250919_5775307.shtml`

### 4.5 离职与当月缴费

武汉公开流程要求离职后由原单位办理停保。武汉还存在`单位职工社会保险当月欠费注销`事项：劳动关系终止并办理停保后，经办机构可根据终止时间认定是否不应缴纳已核定的当月欠费。

来源：

- `https://rsj.wuhan.gov.cn/wechat/rdwt/202311/t20231102_2292746.html`
- `https://rsj.wuhan.gov.cn/zwgk_17/zc/qtzdgkwj/zcfg/202001/P020200108541778661346.pdf`

因此，前端不得使用`15日前 / 15日后`等非官方统一规则自动决定当月缴费结论。劳动合同法中的十五日办理期限是关系转移办理期限，不是缴费日界线。

## 5. 当前代码审查结论

### 5.1 人员档案缺少社保参保事实

`PeopleMember`目前只保存公积金状态和生效月份，没有：

- 劳动关系类型。
- 社保参保结论。
- 参保地。
- 增员、停保状态和生效月份。
- 社保与医保分别办理的结果。

结果是月度社保只能依赖人员类型和静态记录推断。

### 5.2 全职被自动判定为适用社保

`financeSocialInsuranceModel.ts`对所有关系有效的全职人员直接返回`适用`，对非全职直接返回`非全职`。该规则无法表达：

- 已用工但尚未增员。
- 非全日制劳动关系。
- 当月入职、离职和停保生效差异。
- 异地办理或官方办理异常。

### 5.3 月度记录由静态 Mock 初始化

`FinanceSocialInsuranceState`只从`socialInsuranceEmployeeRecords`初始化记录，不会根据人员参保生效区间和月份生成候选。新增人员、新月份和停保变化可能静默遗漏。

### 5.4 状态语义错误

当前状态只有：

```text
待确认 / 已确认 / 延期补缴 / 本月不缴
```

页面允许直接选择延期或不缴；延期记录还会自动复制到下个月。该状态把参保义务、月度核定、欠缴和薪酬扣款混成一个枚举。

### 5.5 当前政策不是期间化计算输入

当前社保配置：

- 只有一个全局启用版本。
- 历史记录编辑时使用当前版本重算。
- 费率缺少完整官方来源证据。
- 计算没有稳定证明执行所属期基数上下限钳制。
- 工伤保险被简化为固定费率，不能表达行业风险和浮动结果。

### 5.6 内部测算直接进入下游

当前员工记录的单位和个人金额由本地政策直接计算。虽然页面存在`社保缴费核定单`概念，但没有结构化保存：

- 官方单位金额。
- 官方个人金额。
- 分险种差异。
- 核定编号和核定时间。
- 差异处理结果。

### 5.7 薪酬和会计下游方向基本正确

当前代码已经做到：

- 已确认个人社保、公积金进入薪酬扣款。
- 个人承担部分参与个税税前扣除。
- 单位承担部分进入公司人工成本。
- 工资计提拆分员工实付、个税、个人社保和个人公积金负债。
- 社保公积金缴费进入资金流水和后续复核。

该部分应复用，不应另建第二套薪酬或付款流程。需要修复的是它消费的上游金额是否真实、稳定和可追溯。

## 6. 目标前端领域边界

### 6.1 单一事实关系

```text
PeopleOrganizationState
  -> 劳动关系、入离职、参保结论和办理事实

SocialInsurancePolicyState
  -> 地区、所属期、险种、基数上下限和费率版本

SocialInsuranceManagementState
  -> 增减员事项、月度候选、测算、官方核定、补缴更正

SalaryManagementState
  -> 只消费已正式确认的个人承担金额

FinanceManagementState
  -> 消费个人代扣、单位负担、实际缴费和回执事实
```

页面不得复制这些状态；Mock 只能初始化相应领域状态，不能在页面内维护第二份事实。

### 6.2 状态所有权

| 事实 | 唯一所有者 | 允许消费者 |
| --- | --- | --- |
| 劳动关系、入离职日期 | `PeopleOrganizationState` | 参保办理、薪酬、人员摘要 |
| 参保义务和办理结果 | `SocialInsuranceManagementState` | 人员档案只读摘要、月度候选 |
| 政策版本 | `SocialInsurancePolicyState` | 月度测算、系统配置只读展示 |
| 内部测算 | `SocialInsuranceManagementState` | 核定差异视图，不进入正式薪酬 |
| 官方核定或正式确认金额 | `SocialInsuranceManagementState` | 薪酬、会计、缴费 |
| 薪酬扣款快照 | `SalaryManagementState` | 薪酬明细、个税、财务 |
| 缴费流水和回执 | `FinanceManagementState` | 流水复核、银行对账、凭证、期间结账 |

### 6.3 页面边界

不新增路由。现有`社保公积金`页面调整为：

```text
社保公积金
  ├─ 参保办理
  │   └─ 人员办理抽屉
  │       ├─ 办理信息
  │       └─ 操作记录
  └─ 月度缴费
      └─ 月度缴费抽屉
          ├─ 人员明细
          ├─ 核定缴费
          └─ 操作记录
```

人员档案只保存和展示人员关系、参保摘要及生效结果，不承载月度核定和缴费操作。

## 7. 目标领域模型

以下类型约束前端内部数据，不代表后端 API 已实现。

### 7.1 劳动关系与参保结论

```ts
type EmploymentRelationshipType =
  | '全日制劳动关系'
  | '非全日制劳动关系'
  | '独立劳务合作'
  | '企业供应商';

type SocialInsuranceObligation =
  | '应参保'
  | '无需参保'
  | '待判定';

type SocialInsuranceNoObligationReason =
  | '劳动关系尚未开始'
  | '劳动关系已于此前结束'
  | '独立劳务合作'
  | '企业供应商'
  | '官方确认无需参保';
```

约束：

1. `无需参保`必须有结构化原因。
2. `员工自愿不缴`、`试用期`、`尚未增员`不得成为原因。
3. `全职 / 兼职`继续作为人员展示类型，但不再作为参保结论的唯一依据。

### 7.2 参保办理档案

```ts
type EnrollmentHandlingStatus =
  | '待增员'
  | '增员办理中'
  | '已增员'
  | '待停保'
  | '停保办理中'
  | '已停保'
  | '办理异常'
  | '不适用';

type SocialInsuranceEnrollmentProfile = {
  personId: string;
  employmentRelationshipType: EmploymentRelationshipType;
  obligation: SocialInsuranceObligation;
  noObligationReason?: SocialInsuranceNoObligationReason;
  insuredRegionCode?: string;
  socialSecurityStatus: EnrollmentHandlingStatus;
  medicalInsuranceStatus: EnrollmentHandlingStatus;
  plannedEnrollmentMonth?: string;
  socialSecurityEffectiveMonth?: string;
  medicalInsuranceEffectiveMonth?: string;
  plannedStopMonth?: string;
  socialSecurityStopEffectiveMonth?: string;
  medicalInsuranceStopEffectiveMonth?: string;
  officialReferenceNo?: string;
  evidenceFileIds: string[];
  updatedAt: string;
};
```

社保和医保允许在同一人员办理抽屉呈现，但必须分别保存生效结果。

### 7.3 缴费基数

```ts
type ContributionBaseSource =
  | '上年度月平均工资'
  | '新入职首月工资'
  | '新入职当年平均工资'
  | '官方核定'
  | '更正';

type ContributionBaseRecord = {
  personId: string;
  policyYear: string;
  regionCode: string;
  source: ContributionBaseSource;
  sourceAmount: number;
  lowerLimit: number;
  upperLimit: number;
  appliedBase: number;
  effectiveFrom: string;
  effectiveTo?: string;
  policyVersionId: string;
  evidenceFileIds: string[];
};
```

计算约束：

```text
appliedBase = min(max(sourceAmount, lowerLimit), upperLimit)
```

不得直接覆盖历史年度基数。

### 7.4 月度缴费记录

```ts
type MonthlyContributionStatus =
  | '待测算'
  | '待申报'
  | '待核定'
  | '核定有差异'
  | '待确认'
  | '待缴费'
  | '已缴费'
  | '欠缴待补'
  | '无需缴纳';

  | '基本养老保险'
  | '职工基本医疗保险'
  | '生育保险'
  | '失业保险'
  | '工伤保险'
  | '住房公积金';

type MonthlyContributionItem = {
  itemCode: ContributionItemCode;
  contributionBase: number;
  employerRate: number;
  employeeRate: number;
  estimatedEmployerAmount: number;
  estimatedEmployeeAmount: number;
  assessedEmployerAmount?: number;
  assessedEmployeeAmount?: number;

type MonthlyContributionRecord = {
  id: string;
  personId: string;
  period: string;
  category: '社保' | '公积金';
  originalPeriod: string;
  handlingPeriod: string;
  eligibilitySnapshot: SocialInsuranceObligation;
  status: MonthlyContributionStatus;
  items: MonthlyContributionItem[];
  estimatedEmployerAmount: number;
  estimatedEmployeeAmount: number;

```

约束：

1. `(personId, category, originalPeriod, correctionVersion)`唯一。
2. 内部测算金额只用于核对，不进入正式薪酬。
3. 进入正式薪酬前必须存在正式确认的个人承担金额。
4. 已确认薪酬或已记账来源不得直接覆盖。
5. `无需缴纳`必须来自参保生效区间或官方办理结果，不允许人工自由选择。

### 7.5 补缴和更正

```ts
type ContributionCorrectionRecord = {
  id: string;
  sourceRecordId: string;
  originalPeriod: string;
  handlingPeriod: string;
  reason: string;
  principalEmployerAmount: number;
  principalEmployeeAmount: number;
  lateFeeAmount: number;
  officialReferenceNo?: string;
  evidenceFileIds: string[];
  salaryAdjustmentPeriod?: string;
  accountingAdjustmentReference?: string;
  status: '待办理' | '待核定' | '待缴费' | '已完成' | '已撤销';
};
```

补缴记录不得修改原记录所属期，也不得自动复制为下月正常缴费记录。

## 8. 目标状态机

### 8.1 入职增员

```text
人员建立劳动关系
  -> 应参保 / 待增员
  -> 增员办理中
  -> 已增员并记录生效月份
  -> 生效月份进入月度缴费候选
```

阻断规则：

- 用工开始超过办理期限但仍未增员，显示办理异常，不转为无需参保。
- 缺少身份证件、参保地或劳动关系起始日时，不能标记已增员。

### 8.2 离职停保

```text
登记劳动关系终止日期
  -> 待停保
  -> 停保办理中
  -> 记录社保、医保停保生效月份
  -> 自动派生离职当月缴费结论
```

离职当月派生规则：

| 条件 | 当月结论 |
| --- | --- |
| 官方停保次月生效 | 当月应缴 |
| 官方确认当月停保且无需缴纳 | 当月无需缴纳 |
| 已核定后官方允许当月欠费注销 | 注销后当月无需缴纳 |
| 官方结果未返回 | 待确定，保留应缴候选 |

### 8.3 月度缴费

```text
待测算
  -> 待申报
  -> 待核定
  -> 核定一致 -> 待确认
  -> 核定有差异 -> 修正来源或登记差异 -> 待确认
  -> 正式确认 -> 待缴费
  -> 实际缴费并形成流水 -> 已缴费
```

### 8.4 欠缴补缴

```text
原期间未完成缴费
  -> 欠缴待补
  -> 创建补缴办理事实
  -> 官方核定本金和滞纳金
  -> 待缴费
  -> 已完成
```

不得存在`延期后下月自动正常扣款`路径。

## 9. 页面与交互方案

### 9.1 人员档案

在现有`任职与薪资`中增加克制的只读摘要：

离职操作保存终止日期后自动产生待停保事项，不出现`是否缴纳离职当月社保`开关。

### 9.2 参保办理视图

列表字段：

```text

```

默认排序：


点击行打开人员办理抽屉。抽屉只使用两个 Tab：

- `办理信息`：参保结论、参保地、增减员、官方生效月份和回执文件。
- `操作记录`：时间、操作人、动作和结果。

### 9.3 月度缴费视图

列表以月份和类别为主事项，不把每位员工全部铺在主页面：

```text

```

- `人员明细`：工号、人员、基数、单位金额、个人金额和核定状态。
- `核定缴费`：内部测算、官方核定、差异、核定文件、缴费回执和关联流水。
- `操作记录`：核定、更正、缴费和回退记录。

### 9.4 系统社保配置

- 单位和个人费率。

- 官方来源及发布日期。

## 10. 薪酬、个税和财务勾稽

### 10.1 薪酬消费门禁

月度薪酬仅消费同时满足以下条件的记录：

1. 人员属于本期应缴范围。
2. 个人承担金额已经正式核定或确认。
3. 所属月份与薪酬计算口径一致。
4. 记录未被更正、注销或替代。

缴费尚未完成不阻断薪酬计算；核定尚未完成必须使薪酬保持`结算中`。

### 10.2 个税口径

社保、公积金个人承担金额进入工资薪金个税扣除时，必须引用薪酬中冻结的本期扣款快照，不能再次读取可变的社保页面记录。

### 10.3 会计口径

正式确认后：

```text
个人承担部分 -> 工资应付中的个人代扣负债
单位承担部分 -> 人工成本及单位负担负债
实际缴费 -> 冲减相关负债并形成资金流水
```

补缴、差异和滞纳金必须分别保存，不能全部覆盖为`社保费`一个金额。

### 10.4 期间结账

期间结账只展示汇总阻断：

- 本期应确认社保公积金事项未完成。
- 应记账社保公积金凭证未记账。
- 按项目既有口径必须完成的缴费、流水复核或回执事项未完成。

期间结账不重复展示人员明细，也不承载增减员、核定或补缴操作。

## 11. 旧模型硬删除清单

1. `全职且关系有效 => 社保适用`的唯一判断。

## 17. 当前阻断项与后续决策

### 17.1 当前阻断项

1. 当前代码没有稳定的劳动关系类型，无法区分独立劳务兼职与非全日制劳动关系。
2. 当前政策参数缺少按所属期可执行的完整官方来源证据。
3. 当前月度记录没有官方核定结构，无法证明薪酬使用的是正式金额。

1. 首版不接官方 API，使用结构化登记和文件证据。
2. 不新增审批；现有财务职责完成核定结果确认。
3. 不新增页面；使用现有模块内部视图和抽屉。
4. 当月离职默认待确定，以官方停保结果形成最终结论。

### 17.3 后端阶段再决策

1. 人社、医保、税务和公积金分别采用 API、文件导入还是人工登记。
2. 官方回执解析、验签、幂等、重复导入和失败重试。
